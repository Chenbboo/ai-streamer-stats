## 1. 阅读顺序与冲突优先级

1. 判断“当前代码已经实现了什么”时，以当前代码、数据库迁移和《系统架构与数据库基线》为准。
2. 判断“接下来应该实现什么”时，以状态为“已确认”的需求或设计文档为准。
3. 同一主题发生冲突时，更新日期更晚的已确认详细设计优先于总体设计；总体设计必须同步摘要和引用详细设计。
4. 直播统计口径以《统计口径说明》为准；珠宝库存、成本、审批和红冲规则以《珠宝ERP第一阶段需求设计》及当前迁移为准。
5. 标记为“历史快照”“历史计划”或“待确认”的文档不得直接作为新开发依据。

## 4. 当前立项流程决策摘要

- 所有有效在职人员可以发起立项申请。
- 申请人就是项目主负责人，不能指定其他人担任负责人。
- 申请人手动填写申请资料、选择归属公司，并从有效且非本人的老板账号中指定审批老板。
- 老板不能审批自己提交的申请。
- 指定老板只审批一次；批准后系统创建正式项目并直接进入 `ACTIVE`。
- 不再设置项目基线二次确认，也不允许老板页面或老板 AI 绕过申请直接创建正式项目。

## 5. 当前 KPI 与结项决策摘要

- 正式项目审批通过后仍只进入一次 `ACTIVE`；尚未发布 KPI 方案时进入老板工作台待办，不增加项目基线二次审批。
- 老板工作台将状态为 `SUBMITTED` 的 KPI 结算列为待确认事项，并提供审核入口。
- 提交验收不提前阻断 KPI 填报；项目在 `ACCEPTANCE` 状态仍可完成填报、提交和退回重提。
- 交付模式“验收通过”和非交付模式“直接结项”是进入 `CLOSED` 的两个受控入口：项目至少存在一个 `PUBLISHED`/`CLOSED` 方案，且所有已发布方案的结算均为 `CONFIRMED`。
- 没有已发布方案、任一方案缺失结算，或结算处于 `DRAFT`、`SUBMITTED`、`RETURNED` 等非确认状态时，服务端必须拒绝结项；未来未到期方案不能提前提交，也会阻断关闭并提示最近结束日期，必须等周期结束、结算确认后再结项。

## 6. 文档变更规则

- 新需求确认后，先更新对应详细设计的版本、日期、状态和修订记录。
- 同一变更必须同步总体设计中的原则、生命周期、权限和验收摘要。
- 描述当前实现的盘点文档不得伪装成目标设计；尚未改造的旧能力应明确标记“旧流程”或“待下线”。
- 历史文档原则上不改写正文，只在顶部补充快照日期、替代文档和使用限制。
- 新增文档后必须登记到本索引，注明“当前基线、实现盘点、待确认或历史快照”。
- 文档中的接口、字段和状态在开发完成前属于目标设计；完成后需要与代码、迁移和测试结果再次核对。

## 7. 发布前一致性检查

- 搜索旧口径：`老板创建项目`、`指定负责人`、`拟任负责人`、`确认项目基线`、`START_PLANNING`、`project.create`。
- 核对申请人、审批老板、归属老板和系统管理员的数据权限。
- 核对页面、接口、数据库字段、AI 能力和验收标准是否描述同一流程。
- 核对页面和 AI 是否都复用验收通过/直接结项的服务端 KPI 门槛，不能仅在前端隐藏按钮或弹出提示。
- 对明确保留的历史术语注明“历史实现”或“旧流程”，避免被当成当前需求。
