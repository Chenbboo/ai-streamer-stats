## 1. 文档目的

本设计用于调整公司经营平台的项目立项流程。

原流程由老板提出并创建项目，再任命项目主负责人。新流程改为公司人员主动提交立项申请，申请人就是项目负责人，由本人手动填写项目资料、选择归属公司并指定审批老板；指定老板一次审批通过后正式创建项目并直接进入执行状态。

本设计覆盖：

- 项目负责人（申请人）和审批老板的职责
- 立项申请、审批、退回、撤回和正式建项流程
- 项目归属、双老板数据隔离和权限边界
- 页面、接口、数据库、AI 和审计调整
- 历史数据兼容与验收标准

本设计是项目立项流程的详细需求基线，《AI驱动公司经营管理平台-总体设计》已同步本次调整；后续若两者再次发生冲突，以更新日期更晚的已确认详细设计为准。老板保留一次立项审批，以及预算决策、负责人变更、暂停、验收、取消和结项等最终经营权限，不再单独确认项目基线。

## 2. 已确认需求

1. 项目不再由老板主动提出和创建。
2. 公司所有有效在职人员都可以发起立项申请。
3. 立项申请由申请人手动填写，不由系统自动生成正式项目。
4. 申请人就是该项目的项目主负责人，不能为其他人员代提立项申请，也不能另行指定拟任负责人。
5. 申请人必须从有效且非本人的 `company_owner` 账号中手动指定唯一审批老板。
6. 归属公司只用于组织与核算，不自动决定审批老板；上海美丸文化公司负责人为江澜、越南 meimaru 公司负责人为王赋章，用于组织管理和人员成本范围。批准前申请不属于正式经营项目。
7. 老板不能通过老板工作台或老板 AI 直接创建正式项目。
8. 老板只审批一次；审批通过即完成立项、创建正式项目并进入执行状态，不再设置项目基线二次确认。
9. 申请、退回、撤回、批准和正式建项全过程必须保留审计记录。

## 3. 角色和术语

### 3.1 立项申请人

立项申请人是实际提交申请的当前登录人员。

- 所有有效在职人员均可成为申请人。
- 申请人必然是项目主负责人，不能指定其他人员担任本次立项的负责人。
- 申请人只能修改、提交、撤回本人创建的申请。
- 申请提交后，除审批老板退回外，申请人不能直接修改已提交内容。
- 审批通过后，系统直接将申请人任命为正式项目主负责人。

### 3.2 审批老板

审批老板由申请人在有效老板列表中手动指定；草稿、退回或撤回状态可以重新选择，提交后内容冻结。

- 同一申请只能有一名审批老板。
- 审批老板同时成为正式项目的归属老板和经营数据隔离边界；项目发起人或负责人变化不改变公司归属。
- 只有所选审批老板可以执行批准或退回；系统管理员可以查看完整材料用于审计和排障，但不能代替老板完成业务审批。
- 另一位老板只能查看申请名称、申请人（即项目负责人）和归属老板等安全目录信息，不能打开申请详情或执行审批。
- 审批老板不能批准自己提交的立项申请；申请人不得通过修改请求参数选择本人或无效账号进行自批。
- 正式立项后，审批老板归属原则上保持不变；更换归属老板属于独立高风险流程，不在本阶段实现。

### 3.3 正式项目主负责人

审批通过并创建正式项目后，申请人自动成为正式项目主负责人。

- 负责完善成员、任务、持续工作、里程碑、风险、KPI、预算说明和人员投入计划。
- 立项审批通过后即可开展项目规划和执行，无需再次提交老板确认。
- 后续负责人变更仍只能由归属老板操作，并保留完整交接记录。

## 4. 总体流程

```text
公司人员创建立项申请草稿
          ↓
申请人手动填写项目资料、选择归属公司和审批老板
          ↓
提交立项申请
          ↓
审批老板审核
  ├─ 退回修改 → 申请人修改后重新提交
  └─ 批准立项 → 创建正式项目
                         ↓
                  申请人成为项目主负责人
                         ↓
                  项目直接进入执行
```

新流程将“提出项目”和“批准项目”分离：公司人员以未来项目负责人的身份发现机会并提出申请，老板一次性判断是否投入公司资源；通过后由申请人直接负责规划和执行。

## 5. 立项申请生命周期

```text
草稿 DRAFT
  ├─ 申请人删除草稿 → DELETED（逻辑删除）
  └─ 申请人提交 → 待审批 PENDING
                       ├─ 申请人撤回 → WITHDRAWN
                       ├─ 老板退回 → RETURNED → 修改后重新提交
                       └─ 老板批准 → APPROVED → 创建正式项目
```

状态规则：

- `DRAFT`：只有申请人可以编辑和删除。
- `PENDING`：申请内容冻结，等待申请人指定的审批老板处理。
- `RETURNED`：必须保存退回原因，申请人可以修改并重新提交。
- `WITHDRAWN`：申请人主动撤回，保留历史记录；需要继续时复制或重新编辑后提交。
- `APPROVED`：审批记录只读，并保存生成的正式项目 ID。
- 已批准申请不能再次批准、退回、撤回或删除。
- 同一申请重复点击提交或审批不得重复创建项目。
- 每次重新提交生成新的提交版本，审批人看到的必须是当前冻结版本。

## 6. 正式项目生命周期

立项申请批准后，系统在同一事务中创建正式项目，初始状态直接为 `ACTIVE`：

```text
老板批准立项
  ↓
创建正式项目并任命申请人为项目主负责人
  ↓
进行中 ACTIVE
```

原有“老板创建项目草稿后再点击进入规划”的 `START_PLANNING` 步骤和项目基线二次确认均取消。申请人应在立项申请中一次性填写老板作出立项决策所需的信息，审批通过后可继续完善成员、任务、KPI、里程碑和执行计划，但不再触发第二次老板审批。

项目进入 `ACTIVE` 后，暂停、恢复、验收、取消、关闭和负责人变更继续沿用现有规则。

## 7. 立项申请表单

### 7.1 必填字段

| 字段 | 规则 |
|---|---|
| 申请标题/项目名称 | 必填，最多 160 个字符；提交时检查重名并提示，不自动合并 |
| 申请人/项目负责人 | 当前登录人员，系统自动填写，不允许前端修改或另选他人 |
| 审批老板 | 必填；从有效且非本人的老板账号中手动选择一人 |
| 归属公司 | 上海美丸文化公司或越南 meimaru 公司 |
| 项目目标 | 必填，说明要解决的问题和可验收结果 |
| 项目类型 | 直播、珠宝、电商、运营、内部、通用或其他 |
| 核算方式 | 盈利型、成本型、价值型或混合型 |
| 管理模式 | 轻量、标准或重点监管；用于决定风险、里程碑、汇报和预算预警强度 |
| 结项方式 | 直接结项、成果验收或阶段验收；与管理模式独立选择 |
| 治理理由 | 重点监管项目必填，其他模式可选 |
| 验收标准 | 成果验收或阶段验收项目必填 |
| 计划开始日期 | 必填 |
| 计划结束日期 | 必填，不能早于开始日期 |
| 预算申请 | 填写金额和币种，或明确选择“不设置预算” |
| 申请理由 | 必填，说明为什么需要公司投入资源 |

### 7.2 选填字段

- 上级项目
- 执行业务来源，例如直播数据管理
- 初步成员建议
- 初步 KPI 或验收标准
- 附件和补充资料
- 备注

### 7.3 字段校验

- 申请人和手动选择的审批老板必须是有效账号。
- 申请人必须处于有效在职状态，并自动作为项目主负责人。
- 所选审批老板必须拥有有效 `company_owner` 角色且未离职、未停用，否则申请不能保存或提交。
- 审批老板不能与申请人相同。
- 上级项目必须与本申请选择同一归属老板，禁止跨老板建立父子项目。
- 归属公司必须是受保护的公司级组织节点。
- 金额使用 `BigDecimal`，预算不能为负数。
- 管理模式仅接受 `LIGHT` / `STANDARD` / `KEY_CONTROL`；结项方式仅接受 `DIRECT` / `RESULT_ACCEPTANCE` / `STAGED_ACCEPTANCE`。
- 阶段验收项目必须设置里程碑；负责人只能在该阶段关联任务全部完成后提交，由归属老板审核。
- 所有用户、公司和项目引用必须使用稳定 ID，名称只用于展示快照。

| 能力 | 公司人员/申请人 | 审批老板 | 其他老板 | 系统管理员 |
|---|---:|---:|---:|---:|
| 新建立项申请草稿 | 是 | 是，但不能自批 | 是，但不能自批 | 是 |
| 查看本人申请 | 是 | 是 | 是 | 是 |
| 修改草稿/退回申请 | 仅本人 | 仅本人申请 | 仅本人申请 | 运维排障只读 |
| 提交/撤回申请 | 仅本人 | 仅本人申请 | 仅本人申请 | 否 |
| 查看完整审批材料 | 仅本人申请 | 是 | 否 | 是 |
| 批准或退回 | 否 | 是 | 否 | 否 |
| 创建正式项目 | 否 | 审批动作触发 | 否 | 审批服务触发 |
| 成为项目主负责人 | 审批通过后自动成为 | 否 | 否 | 否 |

建议新增稳定权限：

```text
business:project:proposal:list       查看本人及与本人相关的立项申请
business:project:proposal:add        创建立项申请
business:project:proposal:edit       修改本人草稿或退回申请
business:project:proposal:submit     提交和撤回本人申请
business:project:proposal:review     审批老板查看、批准和退回
```

上述申请权限不能继续依赖 `project_user` 或 `project_owner` 角色，因为尚未参加任何项目的普通员工同样有权发起申请。建议新增稳定公司级角色 `company_staff`，只表达“有效公司人员”身份，并为该角色授予立项申请页面及本人申请权限。现有直播、珠宝和其他业务角色继续保留，不能因为增加 `company_staff` 而获得其他业务域权限。

人员入职、启用时应根据有效组织归属和在职状态授予 `company_staff`；离职、停用时撤销或禁用其立项申请能力。老板和系统管理员可以通过自身权限访问，但仍受禁止自批规则约束。

`business:project:add` 不再直接暴露给普通页面或 AI。正式项目只能由立项审批服务在批准事务中创建。

### 9.2 申请事件表

建议新增 `biz_project_proposal_event`，保存：

- 申请 ID 和提交版本
- 操作类型：CREATE、EDIT、SUBMIT、WITHDRAW、RETURN、RESUBMIT、APPROVE
- 操作前后状态
- 操作人 ID 和姓名
- 退回或撤回原因
- 操作前后关键字段 JSON 快照
- 操作时间

事件不允许物理删除。

### 9.3 正式项目归属字段

建议在 `biz_project` 中新增：

```text
source_proposal_id        来源立项申请
applicant_user_id/name    原始申请人
sponsor_owner_user_id/name 归属老板
```

现有 `initiator_user_id/name` 当前同时承担“创建人”和“归属老板”语义。改造后所有权限、老板看板、经营核算和父子项目约束统一改用 `sponsor_owner_user_id`。

兼容期可以保留 `initiator_user_id/name`，并与 `sponsor_owner_user_id/name` 同步回填，但新代码不得继续把它解释为实际申请人。页面统一显示“申请人”和“归属老板”，不再显示“立项老板”。

## 10. 批准立项事务

审批老板点击批准时，后端必须在同一数据库事务中完成：

1. 重新读取申请并校验当前状态、版本和审批人。
2. 重新校验申请人、审批老板、公司和上级项目，并确认申请人仍为有效在职人员。
3. 生成唯一正式项目编号。
4. 创建 `biz_project`，状态直接为 `ACTIVE`。
5. 写入申请人、归属老板和来源申请 ID。
6. 建立申请人的 `biz_project_member.OWNER` 关系。
7. 为申请人授予 `project_owner` 和必要的项目参与角色；已有角色时幂等跳过。
8. 写入负责人任命历史，原因标记为“立项申请批准时任命”。
9. 写入正式项目 `CREATE_FROM_PROPOSAL` 事件。
10. 将申请更新为 `APPROVED` 并回写正式项目 ID。
11. 写入申请审批事件和操作审计。

任一步骤失败必须全部回滚，不得出现申请已批准但项目未创建，或项目已创建但申请仍待审批的情况。

## 11. 后端接口调整

建议新增接口：

```text
GET    /business/project-proposal/list
GET    /business/project-proposal/{proposalId}
POST   /business/project-proposal
PUT    /business/project-proposal
DELETE /business/project-proposal/{proposalId}
POST   /business/project-proposal/{proposalId}/submit
POST   /business/project-proposal/{proposalId}/withdraw
GET    /business/project-proposal/review-list
GET    /business/project-proposal/directory
GET    /business/project-proposal/options
PUT    /business/project-proposal/{proposalId}/review
```

`RETURNED` 和 `WITHDRAWN` 状态的再次提交复用 `/submit`，不另设 `/resubmit` 接口。

调整现有接口：

- `POST /business/project` 不再作为人员直接创建项目的入口。
- 正式创建逻辑改为审批服务内部调用，不允许通过前端构造请求绕过审批。
- 项目列表、老板工作台、经营核算、人员职责和项目目录统一按 `sponsor_owner_user_id` 做老板隔离。
- 项目负责人角色在批准时授予申请人，不在申请创建时授予。
- 表单不再提供负责人选择接口或负责人下拉框；审批老板保留必选下拉框，选项接口只返回有效且非申请人本人的 `company_owner`。

服务层必须再次执行数据范围校验，不能仅依赖菜单权限或前端隐藏按钮。

## 12. 前端页面调整

### 12.1 新增“立项申请”页面

建议路由：`/business/project-proposals`

页面包含：

- 我的申请
- 待我处理（仅老板显示）
- 新建立项申请
- 草稿编辑、提交、撤回和重新提交
- 审批详情、退回原因和操作时间线

当前页面使用响应式单页表单，在电脑端和手机端按“基本信息、审批归属、目标周期、核算预算、提交确认”的顺序展示；归属公司与审批老板分别选择。

### 12.2 项目负责人工作台

- 空状态不再显示“老板任命你为项目负责人后才会出现项目”。
- 增加“发起立项申请”入口。
- 增加“我的立项申请”状态卡。
- 申请批准后，新项目自动出现在申请人的负责人工作台，状态为“进行中”。

### 12.3 老板工作台

- 删除“开启项目”按钮。
- 增加“待立项审批”卡片和列表。
- 待办显示申请人（即项目负责人）、公司、预算、周期和申请理由。
- 老板只能批准分配给自己的申请。
- 退回必须填写原因。
- “本人立项项目”统一改为“归属本人项目”。

### 12.4 项目中心

- 删除直接新建正式项目的入口。
- 只展示已批准生成的正式项目。
- 项目列表和详情将“立项老板”改为“归属老板”。
- 增加只读“申请人/项目负责人”和“来源立项申请”信息。
- 正式项目不允许通过编辑接口修改申请人或归属老板。

## 13. AI 能力调整

第一阶段以人员手动填写立项申请表单为正式入口。

- 老板 AI 移除“帮我创建一个新项目”和 `project.create` 正式创建能力。
- 老板 AI 可以新增 `project.proposal.review-list`，查询分配给当前老板的待审批申请。
- 老板 AI 可以准备批准或退回建议，但正式审批仍需老板确认。
- 后续若为普通人员和负责人开放 AI，可允许 AI 帮助整理申请草稿；AI 只能更新本人草稿，不能直接提交或创建正式项目。
- AI 辅助提交申请时需要申请人确认，审批时需要审批老板确认；老板完成一次正式审批后项目直接生效，不再产生项目基线确认。
- AI 历史文本不能作为审批事实，审批材料必须重新读取当前申请版本。

建议能力拆分：

```text
project.proposal.get
project.proposal.draft.update
project.proposal.submit
project.proposal.review.get
project.proposal.review.decide
```

原 `CREATE_PROJECT` 持久化工作流后续迁移为 `CREATE_PROJECT_PROPOSAL`。旧确认单只保留历史兼容，不允许继续生成新的正式项目创建确认单。

## 14. 历史数据与迁移

- 现有正式项目不回退为立项申请。
- 历史项目的归属老板从现有 `initiator_user_id/name` 回填到 `sponsor_owner_user_id/name`。
- 历史项目的申请人优先按现有创建账号回填；无法可靠识别时使用现有立项老板，并标记迁移来源。
- 历史项目不伪造 `source_proposal_id`。
- 迁移不得改变现有项目负责人、状态、经营事实、预算、KPI、人员成本和每日结果。
- 迁移后必须分别使用两位老板账号验证归属项目隔离。

## 15. 审计与安全要求

- 申请人和审批老板全部使用登录账号稳定 ID 校验。
- 前端传入的申请人 ID一律忽略，以当前登录账号为准。
- 前端不得传入独立负责人 ID；正式项目负责人必须由后端使用申请人 ID 建立。
- 审批时重新校验审批老板角色，不能仅依赖申请提交时的权限快照。
- 申请修改、提交、撤回、退回和批准必须记录操作人、时间和版本。
- 不允许申请人修改已提交版本后继续使用旧审批页面批准。
- 同一申请并发审批只允许第一个有效操作成功。
- 审批老板和申请人相同时必须拒绝批准。
- 系统管理员仅用于查看全量申请和审计排障，审批动作仍必须由申请人指定的审批老板执行。

## 16. 验收标准

### 16.1 申请人

- 任一有效在职人员可以创建立项申请草稿。
- 停用账号或离职人员不能创建、修改或提交申请。
- 申请人只能查看和修改本人草稿及退回申请。
- 申请提交后内容冻结，撤回或退回后才能修改。
- 申请人不能通过原项目创建接口绕过审批。

### 16.2 项目负责人

- 申请人就是项目负责人，申请页面不提供负责人选择功能。
- 审批前不获得该正式项目的负责人权限。
- 审批通过后，申请人自动成为唯一有效主负责人。
- 正式项目直接进入进行中，并出现在申请人的负责人工作台。

### 16.3 审批老板

- 只能查看和审批申请人指定给自己的申请。
- 可以批准或填写原因退回。
- 不能批准自己提交的申请。
- 批准后只能创建一个正式项目。
- 只需完成一次立项审批，不再审批项目基线。
- 另一位老板不能打开审批详情或执行审批。

### 16.4 系统管理员

- 可以查看全部申请和审计记录。
- 日常界面不代替老板进行经营审批。
- 紧急操作必须填写原因并保留审计。

### 16.5 数据与事务

- 批准立项时，项目、申请人负责人关系、角色、历史、事件和申请状态必须同时成功或同时回滚。
- 重复提交、重复审批和接口重试不会重复建项。
- 历史项目经营数据和双老板隔离保持不变。
- 项目经营核算按归属老板而不是申请人隔离。

### 16.6 页面与兼容性

- 老板工作台不再提供直接创建项目入口。
- 所有在职人员都能看到立项申请入口。
- 负责人字段固定为当前申请人，不显示人员选择器。
- 项目中心只展示已批准的正式项目。
- 页面不再使用“立项老板”，统一使用“申请人”和“归属老板”。
- 电脑端和手机端均能完成申请、提交、审批和退回闭环。
- 前端通过 `pnpm run build:prod`，后端通过申请人/项目负责人、审批老板、其他老板和管理员四类权限测试。
