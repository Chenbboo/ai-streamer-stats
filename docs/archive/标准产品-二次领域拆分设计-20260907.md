# 标准产品：二次领域拆分设计

> 版本：v1.1（二次调整）
> 日期：2026-09-07
> 状态：需求与领域设计稿，尚未实施、迁移或部署
> 适用关系：本文是 2026-09-07《标准产品蓝图》的增量修订；发生冲突时，以本文的领域边界为准。原项目、直播、珠宝及统计口径中未冲突的部分继续有效。

## 1. 二次调整结论

原方案把通用产品拆成“项目管理、人力资源、财务与管理核算”三个领域，仍不足以承载目标管理、绩效评价和激励分配的独立生命周期。

本次调整后，标准产品采用五个核心管理领域：

1. 项目管理
2. 组织与人员
3. KPI 与绩效
4. 奖金与激励
5. 财务与管理核算

直播运营、珠宝进销存继续作为行业应用；账号、权限、流程、审计、AI 和外部集成继续作为共享平台能力。

“KPI 与绩效”和“奖金与激励”必须是两个独立领域，不能继续合并成“项目 KPI 与奖金”模块。两者可以通过稳定来源和结果快照关联，但不能共用一个状态、一次确认或一张业务主表。

## 2. 参考方式与采用边界

本次参考飞书将目标、绩效、人事与薪酬能力分层协作的产品方式，而不是复制飞书的页面、字段或审批流程：

- 目标管理负责制定、对齐、跟进和复盘目标。
- 绩效评价可以引用目标和业务成果，但有独立的评价、校准和结果确认流程。
- 绩效结果可以作为薪酬和激励的输入，但不会自动等同奖金金额或发放结果。
- 薪酬与激励使用独立方案和处理流程，并与人员、假勤及核算数据协作。

具体状态、角色和字段仍需结合本系统的规模、现有数据和权限设计，不把外部产品宣传材料当作本系统已经具备的能力。

## 3. 五个领域的唯一责任

| 领域 | 负责的核心对象 | 不负责的内容 |
|---|---|---|
| 项目管理 | 项目、计划、任务、投入、成果、验收、交付关闭 | 不定义个人绩效结果，不核准奖金，不确认会计成本 |
| 组织与人员 | 人员主档、任职、组织关系、岗位、外部身份映射、必要的人员有效性 | 不维护项目任务，不计算 KPI，不审批奖金，不保存项目成本事实 |
| KPI 与绩效 | 指标库、目标、周期、指标结果、项目测量、个人/组织评价、校准与结果发布 | 不决定奖金金额，不标记奖金支付，不直接写入成本 |
| 奖金与激励 | 激励方案、适用对象、资格、测算、奖励单、核准、分配及发放跟踪 | 不修改 KPI 结果，不代替绩效评价，不重复维护财务成本 |
| 财务与管理核算 | 预算、费用、内部费率、成本来源、成本确认、调整、项目核算关闭 | 不制定绩效规则，不决定奖励资格，不把成本确认解释为已发奖金 |

领域之间只传递有版本的事实：

```text
项目成果/行业事实 ──> KPI 与绩效 ──> 已发布结果快照
                                      │
                                      v
                              奖金与激励形成奖励单
                                      │
                                      v
                              核算确认成本来源
                                      │
                                      v
                         后续分配/发放只更新支付状态
```

组织与人员为各领域提供稳定人员、任职和组织范围；飞书考勤只提供外部假勤与可用性事实，不直接生成 KPI、奖金或成本。

## 4. KPI 与绩效领域

### 4.1 内部分层

KPI 与绩效领域内部仍需区分两个对象层次：

| 层次 | 用途 | 首批处理 |
|---|---|---|
| 目标与指标 | 公司、部门、项目或个人的目标、指标、权重、目标值、数据来源及周期 | 优先承接现有项目 KPI，允许纯指标方案 |
| 绩效评价 | 对员工或组织进行自评、主管评价、协同评价、校准、发布和申诉 | 先定义接口和边界，完整个人绩效后续建设 |

项目 KPI 是项目成果测量，不自动成为员工个人绩效。个人绩效可以引用项目结果快照作为证据，但必须明确被评价人、评价周期、评价关系和结果发布权限。

### 4.2 建议对象

| 对象 | 关键内容 |
|---|---|
| `MetricDefinition` | 指标编码、名称、单位、计算方式、数据来源、适用范围、版本 |
| `GoalPlan` | 所属组织/项目/人员、周期、目标说明、状态、流程策略版本 |
| `GoalPlanItem` | 指标版本、目标值、权重、责任主体、取数方式 |
| `MeasurementResult` | 实际值、得分、证据、来源快照、提交与确认信息、版本 |
| `PerformanceCycle` | 评价范围、周期、模板、评价关系和时间节点 |
| `PerformanceReview` | 被评价人、自评、主管/协同评价、校准、最终等级和发布状态 |

### 4.3 独立状态

- 目标方案：`DRAFT → PUBLISHED → CLOSED`，可进入 `VOIDED`。
- 指标结果：`DRAFT → SUBMITTED → CONFIRMED`，退回为 `RETURNED`；确认后通过修订或调整形成新版本。
- 绩效评价：`NOT_STARTED → IN_PROGRESS → CALIBRATING → RELEASED`；申诉和更正使用独立记录，不覆盖已发布结果。

纯指标方案不得要求配置奖金阶梯。指标结果确认只生成不可变结果快照和领域事件，不直接生成奖励金额或成本事实。

## 5. 奖金与激励领域

### 5.1 支持的来源

奖励可以来源于：

- 已确认的项目 KPI 或项目成果；
- 已发布的个人/组织绩效结果；
- 独立专项奖励、团队奖励或经营激励；
- 经授权录入的其他业务事实。

因此，奖励必须允许“无 KPI 来源”，KPI 也必须允许“无奖励结果”。来源只决定资格或计算输入，最终奖励金额由激励规则和授权流程决定。

### 5.2 建议对象

| 对象 | 关键内容 |
|---|---|
| `IncentivePlan` | 方案名称、适用组织/项目/人员、预算、币种、生效期、规则版本 |
| `IncentiveRule` | 来源条件、分档/公式、封顶、舍入、冲突与叠加规则 |
| `RewardCandidate` | 来源对象与版本、资格判断、建议金额、计算依据 |
| `RewardAward` | 奖励单、核准金额、受益范围、状态、审批人与版本 |
| `RewardAllocation` | 奖励单到具体人员/团队的分配；未建设个人分配时保持为空，不补造人员 |
| `RewardPayment` | 应付、部分支付、已支付、支付日期及凭证；不再次产生同一奖励成本 |
| `RewardAdjustment` | 对已核准奖励的追加、减少、撤销或冲正依据 |

### 5.3 独立状态

- 激励方案：`DRAFT → ACTIVE → INACTIVE`，已被奖励单引用的版本不可覆盖。
- 奖励候选：`PENDING → ELIGIBLE/INELIGIBLE`，仅表示规则判断结果。
- 奖励单：`DRAFT → SUBMITTED → APPROVED`，可退回 `RETURNED`、拒绝 `REJECTED` 或作废 `VOIDED`。
- 分配状态：`UNALLOCATED → PARTIALLY_ALLOCATED → ALLOCATED`。
- 支付状态：`UNPAID → PARTIALLY_PAID → PAID`；支付失败或撤回保留单独记录。
- 核算状态：由财务与管理核算领域返回 `PENDING/CONFIRMED/ADJUSTED`，不与支付状态合并。

`APPROVED` 只表示奖励金额已经核准，不等于已计入成本、已分配到个人或已经发放。

## 6. 与项目交付和核算的关系

项目交付状态、KPI/绩效状态、奖励状态、核算状态和支付状态必须分别展示：

| 场景 | 项目交付 | KPI/绩效 | 奖励 | 项目核算 |
|---|---|---|---|---|
| 无 KPI、无奖金的内部项目已交付 | 可关闭 | 不适用 | 不适用 | 可保持开放处理费用后关账 |
| 项目已交付、KPI 周期未结束 | 已关闭 | 进行中 | 尚未生成 | 开放 |
| KPI 已确认、不设奖金 | 不受影响 | 已确认 | 不适用 | 不产生奖金成本 |
| KPI 已确认、奖励待审批 | 不受影响 | 已确认 | 待审批 | 尚无已确认奖励成本 |
| 奖励已批准、尚未支付 | 不受影响 | 结果只读 | 已批准/未支付 | 按政策待确认或已确认成本 |
| 奖励已支付 | 不受影响 | 结果只读 | 已支付 | 不重复增加成本 |

任何一个领域的“完成”都不能自动把其他领域推进到终态。项目关闭后，可以继续处理既有 KPI、绩效和奖励；只能补录或更正执行结束日前有依据的项目事实，不能借结算重新开启任务执行。

## 7. 当前代码的耦合点

当前实现仍是“项目 KPI 与奖金”一体化模型，主要耦合如下：

1. `V037__business_project_kpi_bonus.sql` 同时建立 KPI 方案、方案指标、奖金阶梯、结算、结果，并把 `bonus_amount` 放在 KPI 结算中。
2. `BusinessProjectKpiServiceImpl.submit()` 在同一事务内计算 KPI 得分、匹配奖金、确认结算并调用 `recordProjectBonus()`。
3. `BusinessAccountingServiceImpl.recordProjectBonus()` 使用 `KPI-BONUS-SETTLEMENT-*` 作为来源，直接生成已确认成本事实。
4. `frontend/src/views/business/kpi/index.vue` 在一个页面同时发布 KPI、配置奖金阶梯、确认结果和宣告成本入账。
5. `ensureKpiReadyForClose()` 把 KPI 方案和结算完成写成项目结项通用门槛。
6. AI 验收和项目关闭能力复用了同一门槛及“验收通过并结项”的合并语义。

这说明二次拆分不能只调整菜单或表名，必须同时拆服务事务、数据状态、页面入口、权限和 AI 能力。

## 8. 兼容迁移原则

### 8.1 不直接重命名旧表冒充完成拆分

现有表保存已经发布的方案、指标快照、得分、奖金金额、确认人与成本来源。第一阶段保留旧表和旧记录，通过策略版本标识其语义：

- `LEGACY_PROJECT_KPI_BONUS`：旧 KPI 与奖金联动路径；按原责任和金额完成在办结算。
- `METRIC_ONLY_V1`：新纯指标路径；确认结果不产生奖励。
- `INDEPENDENT_INCENTIVE_V1`：新独立激励路径；奖励单引用结果快照或其他来源。

不能把旧 `bonus_amount` 自动迁造成已经分配给个人或已经支付；不能对已确认结果重新套用新规则计算金额。

### 8.2 新数据建议

新版本优先新增独立激励表和稳定来源引用，而不是立即搬迁所有 KPI 历史。现有 KPI 表可先作为项目指标物理实现，通过领域服务隔离；待双读核对通过后再决定是否迁入通用指标表。

奖励成本的幂等身份至少包含组织、来源域、奖励单 ID/版本和成本类别。同一旧 `KPI-BONUS-SETTLEMENT-*` 记录不得再由新奖励单重复生成。

### 8.3 事务边界

- KPI 结果确认事务只保存结果、快照和待处理事件。
- 激励服务消费明确的结果版本或其他来源，形成奖励候选/奖励单；失败可重试，不回滚已确认 KPI。
- 奖励批准后提供待核算来源；核算失败不把奖励改回未批准。
- 成本确认和支付分别幂等，支付状态变化不重复记成本。

首期仍可在模块化单体和同一数据库中实现，不以领域拆分为由提前引入微服务或消息队列。

## 9. 权限拆分

| 权限角色 | 主要权限 | 明确限制 |
|---|---|---|
| 指标管理员 | 指标库、模板和取数规则 | 不审批奖励或查看个人支付凭证 |
| 目标负责人/数据提供人 | 维护目标或提交实际结果 | 不最终确认本人无授权的结果 |
| KPI/绩效复核人 | 确认指标结果、评价或校准 | 不因复核结果而获得奖金审批权 |
| 激励管理员 | 配置激励方案、生成候选和奖励草稿 | 默认不能最终批准自己创建的奖励单 |
| 奖励批准人 | 批准、退回或拒绝奖励单 | 不直接修改已发布 KPI/绩效结果 |
| 薪酬处理人 | 分配和发放处理 | 不改变奖励核准金额；差额走调整 |
| 核算人员 | 成本确认、调整和项目关账 | 不决定奖励资格或绩效等级 |
| 平台管理员 | 配置、审计和技术维护 | 不自动代替业务复核或奖励批准 |

服务端按功能权限、组织/项目范围、对象状态和敏感字段共同校验。菜单可见性不能代替服务层授权。

项目详情只展示有权限的 KPI、奖励和成本摘要及跳转入口。KPI 页面不得继续要求同时配置奖金阶梯；奖励页面必须显示其来源结果版本、审批状态、核算状态和支付状态。

AI 能力按领域注册：查询 KPI 不自动查询敏感奖金，确认 KPI 不触发奖励；生成奖励、批准奖励、确认成本和登记支付是四种不同写操作及确认卡。

## 11. 修订后的首个编码批次（P1-R2）

原 P1 的“项目交付与核算分离”继续保留，并增加 KPI/激励最小拆分。该批必须形成一致的兼容闭环：

1. 为项目交付、KPI 结果、奖励和项目核算分别固定策略版本。
2. 项目交付关闭不再通用依赖 KPI、奖金或费用全部完成。
3. 新增独立项目核算 `OPEN/CLOSED` 及显式关账动作。
4. 新 KPI 方案允许不配置奖金；KPI 结果确认不直接调用奖金成本入账。
5. 新增最小奖励单及审批状态，引用 KPI 结果快照或其他合法来源。
6. 奖励批准后由核算按稳定来源确认成本；个人分配和实际发放仍可留后续，但必须明确显示“未记录”。
7. 旧 KPI＋奖金记录按原路径续办，交付后在项目核算开放时仍可由原责任主体处理，金额和幂等键保持不变。
8. 页面、API、AI、批处理和权限使用同一服务端状态规则。

为降低发布风险，可以在代码开发中分提交实现，但切换一个项目到新策略时，上述数据和服务能力必须已经配套，不能发布“新 KPI 已确认但奖励来源无法处理”的半套业务状态。

## 12. P1-R2 验收情景

| 编号 | 场景 | 预期结果 |
|---|---|---|
| R2-01 | 内部项目无 KPI、无奖金 | 成果符合要求后可关闭交付，之后独立关账 |
| R2-02 | 项目有 KPI 但无激励方案 | KPI 可确认，不生成奖金或成本，项目交付不受阻 |
| R2-03 | 专项奖励没有 KPI 来源 | 经授权可建立奖励单，来源和理由完整，不能伪造 KPI |
| R2-04 | KPI 结果触发奖励候选 | 候选金额不等于已批准；奖励被拒不修改 KPI 结果 |
| R2-05 | 奖励已批准但核算失败 | 奖励保持已批准，显示待核算并可幂等重试 |
| R2-06 | 奖励已批准但未分配/未支付 | 成本状态、分配状态和支付状态分别准确显示 |
| R2-07 | 旧 KPI＋奖金结算在项目交付后办理 | 原负责人/原审核职责可续办，奖金只记一次，历史金额不变 |
| R2-08 | 已关账历史项目 | 不批量重开；调整必须有授权、依据和审计 |
| R2-09 | 页面、直接 API 和 AI 分别确认 KPI | 三个入口均只改变 KPI 状态，不暗中批准奖励或入账 |
| R2-10 | KPI 复核人、奖励批准人、核算人和管理员交叉测试 | 各角色只完成所属动作，跨公司/项目访问被服务端拒绝 |

## 13. 本次不纳入的范围

- 完整个人绩效评价、360 评价、校准、申诉和人才盘点；
- 奖金自动分配到个人、工资单、个税、银行支付和完整发薪；
- 企业会计总账及完整会计期间管理；
- 真实飞书绩效、薪酬或考勤数据联调；
- 重写直播统计和珠宝 ERP 的行业业务规则；
- 将当前模块化单体拆成多个独立部署服务。

上述能力需要先保留清晰接口和状态边界，不以空页面、默认金额或推断状态宣称已经实现。
