## 1. 产品范围与设计依据

项目管理系统管理立项、范围、计划、成员、资源、实际投入、风险问题、项目 KPI、交付验收和结项；提供项目预算与成本视图。人力资源管理系统分别设置组织人员、员工／团队绩效、奖金激励模块，奖励核准及后续个人分配归奖金激励；财务与管理核算系统管成本来源和期间，后续接入外部工资／支付结果。三系统共用平台，直播与珠宝保留行业业务规则。

飞书维护考勤及假勤办理；项目只读取必要的可用性与异常参考。项目工作记录可以按周批量办理，不要求每日打卡或重复请假审批。

正式标准用于校准概念，产品实践用于比较模型；以下具体状态、角色和字段是本产品设计选择，不宣称行业要求采用同一流程。

| 参考 | 采用的经验与边界 |
|---|---|
| [ISO 21502 官方介绍](https://www.iso.org/standard/74947.html) | 项目管理指导适用于不同组织和交付方法；不据此规定固定菜单、固定审批次数或宣称标准认证。 |
| [Microsoft Project 资源单位](https://support.microsoft.com/en-us/project/learn-more-about-resource-units) | 资源分配比例与人员日历共同影响排期，支持区分容量、比例和工作量。 |
| [Asana 时间记录](https://asana.com/features/resource-management/time-tracking) | 预计与实际投入分别记录、比较；计划不能补成已发生的实际数。 |
| [ERPNext 项目成本](https://docs.frappe.io/erpnext/project-costing) | 工时记录与成本费率可以关联；本产品将成本归集和项目执行状态分别管理。 |

首个实施版本不包含自动关键路径排程、完整组合投资管理、合同计费或工资计算；逻辑模型预留关联，不先建设所有高级能力。

## 3. 术语、默认模板与角色

| 术语 | 产品含义 |
|---|---|
| 立项提案 | 说明问题、价值、范围、拟任负责人和粗估投入；申请人可以与负责人不同。 |
| 正式项目 | 已获得有效授权、可组织执行的业务对象；项目编号在组织范围内唯一。 |
| 计划基线 | 经当前治理策略授权的范围、日期、交付物、资源及预算快照，用于比较偏差。 |
| 当前预测 | 对剩余工作、预计完成日和预计成本的最新判断；不覆盖原基线。 |
| 项目指标 | 进度、交付质量、预算或业务目标的度量，允许无奖金关联。 |
| 员工／团队绩效 | 人力资源的绩效管理模块按对象、周期和评价方案形成的结果；可以引用项目指标快照，与奖金激励分别办理。 |
| 验收 | 对某一交付物或阶段给出符合性结论；阶段通过不等于整个项目关闭。 |
| 执行关闭 | 结束正常项目工作，冻结交付和关闭结论；后续结算仍可继续。 |

提供以下模板初值；模板不是客户分叉代码，发布后采用版本引用：

| 模板 | 立项与计划授权 | 验收与关闭初值 |
|---|---|---|
| 轻量协作 | 获授权负责人可自主建项；最低计划齐备时生成首个基线并启动 | 负责人确认成果清单与关闭记录；需要复核时指定独立关闭人。 |
| 受控交付 | 提案由授权人审核；资料齐全时可同次批准基线并启动，否则进入规划 | 指定验收人评审交付物，关闭人确认交接与遗留事项。 |
| 持续服务 | 依授权建项；必须有服务范围、责任人和当前管理周期 | 按周期验收与评估；停止服务时办理整体关闭。 |

产品不强制每个项目二次审批。持续服务可不预填最终结束日，但必须有有限的计划窗口、周期复核日期和退出条件。

| 角色 | 默认业务职责及限制 |
|---|---|
| 发起人 | 编辑本人提案、提交和撤回；不因发起而自动取得所有项目或财务数据。 |
| 项目负责人 | 维护执行计划、分工和预测，提交变更、验收及关闭；同一时点只有一名主负责人。 |
| 成员／任务负责人 | 处理授权任务，记录本人实际投入及成果；代填须单独授权并保留实际人员与代填人。 |
| 资源负责人 | 确认跨项目资源安排、处理超负荷例外；仅看授权范围的容量与分配。 |
| 发起方授权人 | 处理受控立项、重大变更、负责人交接及终止；通过组织策略或项目任命确定。 |
| 验收人／关闭人 | 依据标准处理验收或关闭；受控模板默认不允许申请人自审。 |
| 核算人员 | 管理费率、成本归集与锁期；项目角色不自动获得费率原值或员工工资权限。 |
| 平台管理员／观察者 | 前者维护配置和审计，后者按范围只读；管理员不自动替代业务审批人。 |

同一用户兼任角色时取其明确业务授权；接口、导入、批处理与 AI 均检查动作权限、数据范围、有效任职和对象状态。权限策略不再写死具体老板、公司或姓名。

## 4. 从提案到执行结束的状态

### 4.1 提案状态

| 起点 → 终点 | 动作与角色 | 主要校验及副作用 |
|---|---|---|
| 新建 → `DRAFT` | 发起人保存草稿 | 保存组织、模板版本、目标、拟任负责人；草稿允许未完整。 |
| `DRAFT`／`RETURNED`／`WITHDRAWN` → `SUBMITTED` | 发起人提交受控提案 | 必填范围、授权路径、日期或计划窗口；冻结提交版本，生成待办。 |
| `SUBMITTED` → `WITHDRAWN` | 发起人撤回 | 审批尚未完成，收回待办，保存原因；审批并发以版本锁判定唯一结果。 |
| `SUBMITTED` → `RETURNED`／`REJECTED` | 授权人退回修改／否决 | 意见必填；退回可改版重提，否决终止本次提案，后续复制为新提案。 |
| `SUBMITTED` → `APPROVED` | 授权人批准 | 当前提交版本与权限有效；原子创建唯一项目，记录人工批准来源。 |
| `DRAFT`／`RETURNED`／`WITHDRAWN` → `APPROVED` | 获授权负责人自主启动 | 仅自主模板可用；完整计划校验通过，记录 `SELF_AUTHORIZED`，不伪造审批人。 |

`APPROVED`／`REJECTED` 为提案终态；批准提案只读。只允许无提交历史的草稿逻辑删除，重复批准或重试不得重复建项。

### 4.2 正式项目状态

| 起点 → 终点 | 动作与角色 | 主要校验及副作用 |
|---|---|---|
| 批准提案 → `PLANNING` | 系统依据批准结果建项 | 授权已成立，详细计划未齐；不代表已启动执行。 |
| 批准提案 → `ACTIVE` | 同次授权启动 | 首个基线齐备，保存基线及授权记录；轻量模板支持此路径。 |
| `PLANNING` → `ACTIVE` | 负责人发布计划／授权人确认计划 | 按模板一次完成所需确认；范围、工作项、责任人、日历和交付标准齐备。 |
| `ACTIVE` → `ON_HOLD` | 负责人或授权人暂停 | 原因、复核日必填；停止新周期任务生成，处理未开始分配，不自动取消已有记录。 |
| `ON_HOLD` → `ACTIVE` | 有权人员恢复 | 复核剩余计划与资源，必要变更批准后恢复；保留暂停区间。 |
| `ACTIVE` → `CLOSING` | 负责人申请关闭 | 交付清单、验收依据、实际执行结束日和关闭检查快照齐备。 |
| `CLOSING` → `ACTIVE` | 负责人撤回／关闭人退回 | 原因必填；旧关闭申请保留，已通过验收不静默失效。 |
| `CLOSING` → `CLOSED` | 关闭人确认；轻量模板可负责人确认 | 对当前版本重跑关闭校验，固化结论及交接，停止未来正常工作。 |
| `PLANNING`／`ACTIVE`／`ON_HOLD`／`CLOSING` → `CANCELLED` | 授权人批准终止 | 保存原因、终止日期、剩余工作和合同等义务的处置，终止不同于交付成功。 |
| `CLOSED`／`CANCELLED` → `ACTIVE` | 授权人批准重新开启 | 独立重开申请、必要资源与计划、版本审计；已锁核算期间不随之解锁。 |

暂停期间允许补录已发生投入、复核成果和处理问题；新增应急工作需明确授权。关闭中冻结关闭范围，需返工或扩范围时退回执行。

所有迁移写入原状态、目标状态、动作人、业务角色、理由、模板与工作流版本、请求标识及时间；提交材料版本变化后，旧审批不得继续执行。

## 5. 计划、变更、任务和持续工作

首个基线至少含范围说明、验收定义、负责人、计划窗口、一项工作或交付安排、适用日历。预算模块未启用时不强填金额；启用时区分未估算、已估算为零和已批准预算。

基线包含不可变的范围、里程碑、任务计划、资源计划及预算引用快照。当前计划可滚动维护，比较时同时展示原始基线、最新批准基线和当前预测。

变更采用 `DRAFT → SUBMITTED → APPROVED／RETURNED／REJECTED`；待审可撤回为 `WITHDRAWN`，退回或撤回后可修订重提。申请保存原基线、新值、原因及范围／日期／工作量／预算影响；批准原子生成新基线版本，旧版不覆盖。

模板定义需审批的范围、关键日期、预算上限、负责人和关闭规则变更。默认日常任务分工、说明及预测更新由负责人处理；改变已批准交付承诺需授权。不能通过先降低关闭规则，再关闭项目来绕过应有批准。

首期记录依赖和冲突，不自动声称具备完整排程引擎。父子任务和依赖图均禁止循环；跨项目依赖必须有双方可见的受限引用，未授权者不获得对方详情。

任务建议状态为 `TODO → IN_PROGRESS → IN_REVIEW → DONE`；无独立评审时可按模板直接完成。退回回到 `IN_PROGRESS`；`BLOCKED` 作为阻塞标记并记录原因和解除条件，避免与生命周期互斥。撤销任务使用 `CANCELLED`，已完成任务返工须保留旧成果版本。

工作量、完成比例和完成数量独立：完成 50% 的工作量不等于交付完成 50%；里程碑作为零工期检查点，本身不重复归集子任务工时。父任务展示汇总时不得再累计父级同一来源数值。

持续工作由“规则＋周期实例”构成：规则保存负责人、频率、时区、起止期和标准；每期生成独立可完成的工作实例。规则版本与周期起点形成幂等键，暂停、改频率或停止时不重建已生成实例，不修改历史完成量。

允许记录项目级工作量而不强制拆到任务，但须选择活动类别；启用任务成本分析的模板可要求任务关联。任务进度或行业完成数量不能自动转换成确认工时。

## 6. 资源、投入与成本口径

| 概念 | 保存与计算规则 |
|---|---|
| 工期 | 根据项目／任务日期、工作日历计算的跨度；多人同时参与不会简单倍增工期。 |
| 资源容量 | 员工有效日历中的可工作分钟，扣除已确认不可用区间；保留来源与版本，缺数据时标明未知。 |
| 分配比例 | 某时间段计划使用可用容量的比例；转换成逐日计划分钟用于跨项目比较。 |
| 计划工作量 | 独立输入人时／人天或由分配比例推导；二者择一作为该分配的计算依据，不能重复相加。 |
| 实际工作量 | 由人员／授权代填人记录的实际劳动投入；无记录就是未记录，不能回退计划值。 |
| 人天 | 工作量显示单位；换算基准是有效单位政策中的分钟／人天，并非自然日或任意考勤天。 |
| 内部费率 | 核算维护的币种、计价单位、生效区间及版本；与出勤和员工实际工资区分。 |

例如日历每天 8 小时、五个工作日，分配 50% 可形成计划 20 小时；实际确认 18 小时，在 8 小时／人天的政策下显示 2.25 人天。以上数值是示例，不是写死的产品参数。

推荐以整数分钟保存实际工作量，同时保留输入数量、`HOUR／DAY`、换算政策与分钟／人天快照；前端转换预览后按分钟精度提交，不能后台静默舍入。资源日历变为 6 小时，不自动把已记录的 1 人天从 8 小时改成 6 小时。

资源分配按人员和实际参与日期建模，不继承整个项目周期。项目级资源预留与任务分派共用分配引用，任务细分消耗预留，不能两个层级重复占容量。

按人员、业务日期、时区汇总所有项目的逐日计划分钟，资源冲突按每日有效容量识别，不能仅求跨整个区间的百分比之和。超负荷提示给资源负责人，可记录例外与依据；实际投入超计划本身不禁止填报。

飞书假勤变更更新未来可用性预测并提示受影响分配；不改已批准基线或实际投入，不把请假直接变成零成本。同步失败时显示数据更新时间与未知状态，不推断员工缺勤或全勤。

无资源计划也可由有效成员补录实际工作，须说明未计划活动；无项目授权人员进入补录授权流程。存在已生效假勤冲突时发出待核对事项，由相应负责人说明并处理，保留飞书源事实。

确认投入向核算提供来源记录、日期、人员、项目、工作量和版本。标准费率方法以确认工作量及适用费率计价；没有费率时为“已确认投入、待计价”，不能记成零。预算估算与实际成本分栏。

费率跨生效日时逐日适用并保留快照；实际薪酬分配若启用，需按成本对象和期间明确替代或补充政策，防止重复归集。项目汇总金额不等于工资、奖金已批准或支付成功。

## 7. 实际工作记录的完整流程

实际记录按行归属一个人员、项目和工作日期，可分到任务／持续工作实例；按日或周批量提交是操作便利，不引入另一套考勤考核制度。

| 状态迁移 | 操作与约束 |
|---|---|
| 新建 → `DRAFT` | 本人或授权代填人录入日期、活动和数量；允许修改及删除未提交草稿，不生成实际成本。 |
| `DRAFT`／`RETURNED`／`WITHDRAWN` → `SUBMITTED` | 校验实际日期不在未来、有效参与授权、数量为正、换算有效；冻结本次提交版本。 |
| `SUBMITTED` → `WITHDRAWN` | 未处理前由提交人撤回；与确认并发时仅一个状态迁移成功。 |
| `SUBMITTED` → `RETURNED` | 本项目投入确认人退回，理由必填；不能代填修改数量后直接确认。 |
| `SUBMITTED` → `CONFIRMED` | 本项目负责人或授权确认人批准；本人记录默认交另一授权人，业务策略明确允许自确认时单独审计。 |
| `CONFIRMED` → 更正申请 | 原记录保持有效只读；申请保存原版本、新值及理由，经原确认职责或接任人复核。 |
| 更正批准 → 新有效版本 | 原版本记为 `SUPERSEDED`，新版本成为唯一有效确认值；同步核算差额或冲正，保留全链路。 |

更正可将有效工作量归零以撤销错误记录，须明确撤销原因；归零是更正结果，不能用零行冒充已工作。更正被拒绝或未批准时不影响原有效记录。

同一来源记录仅能存在一个有效版本；一次日汇总导入与明细导入不得同时归集。提供时间段时禁止同一人员的实际时间段重叠；仅提供数量时只能验证总量与来源重复，不能宣称已消除所有重叠。

跨项目日总量在提交及确认时均重新验证，对同一人员及日期的并发确认采用聚合锁或等效一致性控制；超过日历容量要求说明，明显超出人员该本地日实际时长则拒绝。跨夜按员工时区拆日，保留区间与转换依据；含夏令时地区不能固定认为每个自然日都是 24 小时。

确认状态更新和待发布业务事件同事务落库；核算以来源＋版本对处理事件去重。成本按稳定来源保持唯一有效值，更正只生成差额或关联冲正，不累计各版本全额。核算失败标为待处理并可重试，不悄悄撤销已确认的工作事实或生成重复金额。

## 8. 验收、关闭及关闭后的业务

交付物保存验收标准版本与成果版本。验收申请 `DRAFT → SUBMITTED → ACCEPTED／RETURNED`；退回后新版本重提，结果说明和评审人可追溯。阶段验收独立，整体验收引用已通过的阶段记录。

验收人确认具体成果而非笼统的任务百分比。允许受控的附条件验收，但必须列出遗留项、责任人、期限、接收方和影响；影响核心交付标准的问题默认阻止验收，豁免需要有权方说明及批准。

关闭检查分为不可绕过的完整性校验与模板业务规则：前者包括权限、版本、有效验收引用及数据一致性；后者可要求阶段通过、投入整理、合同资料或核算条件。HR 绩效与奖金完成默认不阻止项目关闭。

关闭人逐项处理未完任务、风险、问题及未确认投入：完成、取消、保留为结算待办或转交已有接收对象。高风险和关键义务不能只标“忽略”；需要明确接收人接受转交及依据，关闭快照保留其最终归属。

执行结束日与审批关闭时间分别保存。关闭后不再生成正常持续工作或新的未来分配，未完成任务以取消／转交记录处理，不伪造完成；后续服务应进入接收的服务周期或新项目。

| 关闭后操作 | 默认边界 |
|---|---|
| 既有周期项目 KPI、奖励和费用处理 | 项目 KPI 在项目系统续办；奖励在 HR 奖金激励、费用在财务与管理核算依各自权限和状态续办，不需先重开项目。 |
| 员工／团队绩效、个人分配及支付〔后续能力〕 | 启用后分别在人力资源绩效管理、奖金激励及财务／外部工资支付系统办理；项目只展示授权关联摘要，不默认展示个人评分、分配或支付明细。 |
| 补录或更正执行结束日前的实际投入 | 可走专用补录／更正授权，保留原因与关闭版本；不能更改交付结论。 |
| 成本重计价、差额或冲正 | 先校验项目结算开放或取得调整授权，再依核算期间规则处理；已锁期间走核算调整流程，执行重开不能越过锁期。 |
| 更新遗留项进度、交接回执、审计说明 | 仅授权字段可变，保留事件；不得借此新增未授权项目范围。 |
| 执行结束日后的新项目工作 | 默认拒绝计入旧执行期；选择接收项目／服务周期，确需恢复执行时走重开流程。 |

项目展示执行状态、项目核算状态、项目 KPI 与授权奖励／费用待办；启用后续绩效、支付及期间管理能力后，才按权限关联其独立状态。关闭项目仍可显示“项目指标待确认、费用待结算、奖金待确认”，不能汇成一个模糊的“全部完成”。

还要区分项目结算开放状态与会计期间状态：项目 `accountingState=OPEN／CLOSED` 表示该项目是否允许继续结算，期间 `LOCKED` 表示该期间不允许普通追溯入账。开放项目结算不等于解锁期间；最终状态名称由核算设计统一。

## 9. 逻辑实体与约束

以下名称仅为建议逻辑名，不是已存在的表、API 或迁移承诺；物理映射在实现阶段按现有 RuoYi 模块评估复用。

| 逻辑实体 | 关键字段与约束 |
|---|---|
| `ProjectTemplateVersion` | 模板标识、版本、立项模式、计划授权、验收与关闭策略、启用模块；已引用版本不可覆盖。 |
| `ProjectProposal` | 组织、提案号、申请人、拟任负责人、授权路径、状态、提交版本、授权来源、生成项目 ID；同提案最多一项目。 |
| `Project` | 组织、编号、父项目、负责人、模板版本、工作流版本、状态、实际起止日期、关闭时间、当前基线 ID；父子关系无环。 |
| `ProjectMembership` | 项目、员工、角色、有效起止日、授权范围；同一时点唯一主负责人，历史离任不删除。 |
| `PlanBaseline` | 项目、序号、范围与计划快照、预算引用、授权人及依据、批准时间、内容摘要；项目＋序号唯一且不可变。 |
| `ChangeRequest` | 项目、原基线、拟变更快照、影响、提交版本、状态和审批；批准时检查原基线仍有效。 |
| `WorkItem`／`WorkDependency` | 项目、父项、负责人、任务类型、状态、阻塞、计划日期、预测及完成日期、依赖及滞后；禁止跨项目伪关联和依赖循环。 |
| `RoutineDefinition`／`RoutineOccurrence` | 规则版本、时区、频率、有效期、实例期起点及工作项 ID；规则＋版本＋周期唯一，停止不删旧实例。 |
| `Milestone`／`DeliverableVersion` | 项目、目标日期、验收标准、成果版本、附件引用和阶段关系；成果版本不能覆盖已审材料。 |
| `AcceptanceReview` | 验收对象与版本、申请人、验收人、提交版本、状态、结论、遗留项引用；同对象版本最多一个待评审。 |
| `RiskIssue`／`HandoverItem` | 类型、等级、责任人、状态、应对措施；转交需接收对象、接收人和接收证明，关闭后可追踪。 |
| `ResourceAssignment`／`DailyAllocation` | 人员、项目／任务、日期、输入方式、数量或比例、日历和单位政策版本、逐日分钟、预留引用；同来源不重复占用。 |
| `WorkCalendarVersion`／`AvailabilitySnapshot` | 日历、时区、有效日期、工作区间、不可用区间、来源及更新时间；飞书事实只读，未知与零容量不同。 |
| `WorkEntry`／`WorkEntryRevision` | 逻辑记录 ID、项目、员工、业务日及时区、活动、原始单位数量、分钟、换算快照、状态、来源及版本；唯一有效确认版。 |
| `WorkCorrection` | 原记录版本、拟更正值、原因、申请与复核人、状态、新版本引用；原版本已变化时须重新评审。 |
| `ProjectMetricSnapshot` | 指标定义版本、周期、目标、结果、单位、来源版本、采集时间及质量；不直接生成员工评价或奖金。 |
| `ProjectCostReference` | 核算成本记录 ID、来源工作记录及版本、计价状态、金额币种、费率引用；项目仅引用授权结果。 |
| `ProjectClosure` | 项目、执行结束日、关闭版本、检查结果、验收引用、转交及结算待办、结论、关闭人；历史版本只读。 |
| `DomainEvent`／`IntegrationOutbox` | 事件 ID、组织、对象、版本、动作人、来源、请求幂等键、发布时间及消费状态；失败可重试，不重复产生业务结果。 |

通用字段至少包括业务归属组织、稳定主键、创建／修改审计和乐观锁。首轮业务人员标识沿用现有 `sys_user.user_id`；外部身份映射主要用于飞书接入，不要求新建员工主键或迁移全部人员引用，不能把姓名当主键。未批准公有云多租户建设，本设计不预设租户计费或跨租户共享。

日期范围统一约定：界面业务起止日均包含，实际时段采用起点包含、终点不包含；所有换算带业务时区。工作量使用整数分钟，金额使用定点小数和币种，不能用浮点金额或把币种换算规则隐藏在项目页。

## 10. 历史兼容与实施验收

第 4—9 节描述最终目标，不要求第一批一次重写全部状态和实体。与总体实施清单对齐，过渡范围如下：

| 阶段 | 本文相关交付与限制 |
|---|---|
| P1：版本化解耦 | 引入按项目生效的流程策略，区分执行关闭与项目结算 `OPEN／CLOSED`；先复用可用状态，不强制迁移全部提案或验收枚举。 |
| P1：后续办理通路 | 仅切换到分离策略的项目，依权限允许交付关闭后的既有 KPI／费用结算；配套处理服务、页面和 AI 的终态限制，不能只删除关闭校验。 |
| P2／P3 | 依实施清单建设新实际投入、模板基线、项目指标和独立奖励核准及成本来源。 |
| 后续产品版本 | HR 绩效管理中的完整员工／团队绩效、HR 奖金激励中的个人分配，以及财务／外部工资支付结果接入；不能把旧 KPI 表改个名称就视为员工绩效或工资发放。 |

未切换的旧项目保留旧规则，既有已关闭项目结算不批量重新开放；历史义务的特批办理须明确项目范围、操作权限、依据与审计。P1 仅以对应过渡情景验收，下面最终目标情景分批启用。

旧数据保留原始状态、原工作流、日期和成本版本，新增可解释的版本标识。旧 `APPROVED` 可能来自 `OWNER_LAUNCH` 或人工批准，依据事件区分；没有证据时标“历史来源待核实”，不能补造审批。

新状态建议不直接覆盖旧 `PAUSED／ACCEPTANCE／CANCELED`；兼容映射必须依据业务语义与事件，旧验收中不必机械等于新关闭中。在途项目切换先列待审提案、投入、假勤、KPI 和核算义务，再形成迁移清单及确认记录。

旧百分比记录保留原值、来源和历史金额。只有日期、日历、单位与确认依据充分时才生成带来源的换算记录；`PLAN_DEFAULT` 不升级成员工填报实际。存量记录核对及核算样本对账属于实施门槛，本次未访问生产数据库，未完成真实样本验证。

| 编号 | 验收情景与预期 |
|---|---|
| PM-01 | 轻量内部项目无 KPI、无奖金，自主授权启动并生成基线；成果和关闭检查齐备后可关闭，审批来源准确。 |
| PM-02 | 受控提案重复批准、撤回与批准并发，只创建一个项目；资料完整可一次批准启动，缺详细计划进入规划。 |
| PM-03 | 负责人修改预测结束日，原基线不变；申请调整合同交付日后只有有权人批准才生成新基线。 |
| PM-04 | 一人跨两项目部分参与，以各日有效容量识别冲突；项目预留再分给任务不重复计算，人员日期不继承全部项目工期。 |
| PM-05 | 8 小时／人天记录 0.5 天为 240 分钟，日历或政策后续改变不改历史；跨夜记录正确拆日并保留时区。 |
| PM-06 | 仅有计划没有实际，不产已确认工作量；未计划的有效成员投入可说明后提交，超计划不等同超出自然日实际时长。 |
| PM-07 | 实际草稿、提交、退回、确认、更正各有版本；核算事件重复投递只计一次，缺费率显示待计价，锁期后通过调整处理。 |
| PM-08 | 飞书确认请假或撤销后更新可用性并提示冲突；不自动删工作记录、不生成零成本，接口失败不判缺勤。 |
| PM-09 | 持续工作跨时区重复生成只得到一个周期实例；暂停不生成未来实例，已完成数量不随规则修改。 |
| PM-10 | 阶段验收通过而其他阶段未完不能误关项目；关键遗留项未经接收不能关闭，合法转交后保持跟踪入口。 |
| PM-11 | 项目关闭后员工绩效、奖金和费用继续办理；可受控补录关闭前投入，不能直接录入关闭后新工作，重开不解锁核算期间。 |
| PM-12 | 成员、创建人、验收人、资源负责人、核算人员及管理员分别验证范围；历史自主建项与人工审批正确区分，旧成本总额保持可对账。 |
