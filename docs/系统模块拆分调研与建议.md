## 1. 产品方向与结论

用户已明确：以标准产品为目标，参考行业通用模型，先不考虑本公司个性化要求。本版本据此替代此前围绕“只用天、奖金独立、假勤可停用”形成的八个并列子系统建议。

推荐采用 **3 个通用产品域 + 2 个行业应用 + 共享平台**：

| 层次 | 产品域／应用 | 模块边界 |
|---|---|---|
| 通用产品 | 项目管理 | 项目治理、目标范围、计划与任务、里程碑、交付、资源计划、实际投入、项目预算成本、风险问题、变更和结项 |
| 通用产品 | 人力资源管理（HCM） | 组织人员、任职关系、假勤、绩效、薪酬激励；奖金属于薪酬激励能力 |
| 通用产品 | 财务与管理核算 | 费用、收支、成本政策、成本归集与分摊、预算控制和经营报告；总账、应收应付、支付等按产品范围建设或集成 |
| 行业应用 | 直播运营 | 主播、直播日报、客户维系、业务指标和行业数据来源 |
| 行业应用 | 珠宝进销存 | 商品、供应商、采购、销售、库存、盘点、组装和行业单据规则 |
| 共享平台 | 平台基础服务 | 身份权限、组织标识、审批待办、通知、附件、审计、配置、集成、报表及 AI 接入 |

这是对当前业务的推荐分层，不是 ISO 或某个厂商规定必须拆成五套系统。绩效、薪酬、假勤可以有独立应用入口与权限，仍归同一个 HCM 产品域；若以后独立销售或部署，再按实际产品战略决定。

产品域、功能菜单和部署服务是三个层次。现阶段可以继续使用现有 Vue、Spring Boot 和 RuoYi，在同一平台内建立清楚的模块边界，不把“标准产品”直接等同于微服务拆分。

用户进一步说明考勤已在飞书运行。本产品的假勤能力建议通过飞书集成提供：飞书维护规则、打卡、假勤审批和考勤结果，网站按权限同步和使用结果，不再并行建设另一套考勤办理流程。该选择是标准模块采用外部服务的集成方式，不改变项目投入与考勤的业务边界。详见第 9 节。

## 2. 正式标准与产品实践分别用于什么

| 依据 | 公开资料支持的内容 | 本项目的使用方式 |
|---|---|---|
| ISO 21502:2020 | 提供适用于不同组织、项目和交付方法的项目管理高层指导；并非企业软件菜单规范。[ISO 官方范围介绍](https://www.iso.org/standard/74947.html) | 用于校准项目管理范围和术语；不能据此声称系统应有固定数量菜单或已通过认证。 |

| Zoho People | 员工、假勤、绩效、薪酬具有不同模块，薪酬支持奖金并与 Payroll 集成。[功能介绍](https://www.zoho.com/people/features.html) | 组织人事、假勤、绩效和奖金不应按同一粒度各算一个独立产品域。 |
| SAP SuccessFactors | 绩效目标与薪酬有分别的产品能力；Variable Pay 模块处理员工浮动薪酬资格和计算。[绩效目标](https://www.sap.com/products/hcm/performance-goals.html)、[浮动薪酬](https://help.sap.com/docs/successfactors-compensation/implementing-and-managing-variable-pay/sap-successfactors-variable-pay) | 绩效结果可作为激励输入，但评价、奖励确认与发放保留各自流程。 |

| ERPNext / Frappe HR | 项目成本可由任务时间记录和成本费率计算；请假申请与薪资附加项在 HR 中分别管理。[项目成本](https://docs.frappe.io/erpnext/project-costing)、[假勤](https://docs.frappe.io/hr/leave-application)、[薪资附加项](https://docs.frappe.io/hr/additional-salary) | 项目、HR 与核算通过明确来源关联；项目预算和成本视图可以留在项目内。 |

“行业标准”需要区分正式标准、厂商实践和我们的设计判断。上表中的菜单归属与三域分层是参考多家产品后提出的架构建议，并非各厂商完全相同，也不是标准条文的逐字要求。

## 3. 前一版必须修正的判断

| 前一版方向 | 标准产品方向 |
|---|---|
| 公司经营六个系统，与直播、珠宝合计八个并列系统 | 先按产品域分层，再在域内划分模块；不以菜单数量决定系统数量。 |
| 取消百分比，人员投入一律按天 | 区分计划容量、计划工作量和实际投入；可支持百分比、人时和人天，单位换算受工作日历约束。 |
| 奖金是与项目、人事并列的产品 | 奖金归薪酬与激励模块，可独立入口；项目奖金池只是其中一种来源或场景。 |
| 请假从项目抽出后优先停用 | 假勤属于 HCM 的标准能力；是否首期实现、通过集成获得或以后建设，由产品版本规划决定。 |
| KPI 全部移到绩效系统 | 项目交付指标与员工绩效指标先区分语义；项目度量留在项目，人员评价归 HCM 绩效。 |
| 项目只管任务成果，预算成本全部放外面 | 项目需要预算、资源和成本控制；核算负责金额来源、政策与核算结果，双方通过明确接口协作。 |
| 去掉所有结项前的跨模块检查 | 建立有默认值且可配置的关闭检查；验收、合同或财务要求按项目类型确定，不能把特定奖金结算写死为所有项目的必经步骤。 |

## 5. 标准能力目录与来源边界

| 产品域 | 标准能力模型建议 | 数据和流程职责 |
|---|---|---|
| 项目管理 | 立项与项目类型、目标范围、工作分解、任务依赖、计划基线、资源分配、实际投入、里程碑、风险问题、变更、项目预算成本、验收、结项复盘 | 管理工作和交付；提供实际项目投入、成果与项目维度，不维护员工出勤或实际工资。 |
| HCM：组织人员 | 法人／公司、部门、岗位、人员任职关系、人员状态、员工与经理自助 | 管理人员主档和任职事实；登录身份与业务身份关联但不等同。 |
| HCM：假勤 | 工作日历、班次、出勤、休假类型与额度、申请审批、加班和异常处理 | 管理出勤与休假；为排期提供可用性，不能直接把公司用人成本定义为零。 |
| HCM：绩效 | 考核对象、周期、指标与权重、结果来源、评价、复核与结果档案 | 管理人员评价；项目结果可以被引用，不将一个项目的得分直接等同员工绩效。 |

| 财务与管理核算 | 预算控制、费用收支、成本对象与成本中心、成本政策及费率、归集分摊、项目核算、期间和报告 | 维护金额依据和财务／管理核算记录；需要完整财务产品时再定义总账、应收应付、支付等建设或集成范围。 |
| 平台基础服务 | 组织与身份标识、角色及数据权限、可配置审批、通知待办、附件、审计、字典、接口与集成、报表和 AI | 统一技术与协作能力；审批业务规则仍由各模块控制，统一待办不取代业务对象。 |

该目录描述标准产品需要考虑的能力，不代表本轮一次开发全部功能。应逐项标明现有能力、待改造能力、后续能力和外部集成，并形成版本路线图。

项目、HR 和核算不共享一个万能状态字段。即使统一工作台显示了所有事项，项目状态、绩效状态、奖励状态、成本入账状态和付款状态仍分别维护。

## 6. 资源、工时、考勤和成本的统一术语

| 术语 | 含义 | 示例 |
|---|---|---|
| 工期 | 按日历和排期定义的工作跨度 | 一个任务安排在一周内完成 |
| 资源容量 | 人员按工作日历可投入的时间 | 某周可用 40 小时 |
| 分配比例 | 计划占用可用容量的比例 | 该周计划给项目 A 分配 50%，即 20 小时 |
| 计划工作量 | 预计完成工作的投入 | 预计 20 人时；若配置 8 小时／人天，则为 2.5 人天 |
| 实际工作量 | 根据项目／任务实际工作记录形成的投入 | 实际记录 18 人时 |
| 出勤 | 按假勤规则记录的在岗或工作状态 | 当周出勤记录，并不自动说明时间投入哪个项目 |
| 内部成本费率 | 用于管理核算的成本标准及生效版本 | 每小时或每天的内部标准成本 |
| 实际项目人工成本 | 按产品明确的核算方法和实际依据形成的金额 | 确认投入与适用费率计算；实际薪酬分配属于另一个可选核算来源 |

示例中的 40 小时、8 小时等只说明概念，不作为产品固定政策。标准工作日、节假日、兼职、班次、时区和换算单位需要按有效日历配置。

产品建议：

- 同时保留资源计划与实际记录，明确计划、估算、已确认实际的状态及数据来源。
- 人时／人天按配置换算；百分比用于资源容量和计划，不是替代所有实际记录的唯一方式。
- 成本方法可明确区分标准费率核算与实际薪酬分配，不能混算或重复归集同一人员成本。
- 工资、费用、奖金入账和付款不是同一个概念；项目成本金额不自动代表已向员工支付。
- 保留政策、日历、费率和结果版本；缺少依据时标为待完善，不虚构实际数。
- 按天展示可以是视图设置，不能限制通用数据模型只能存天。

## 7. 标准产品应具备的可配置边界

以下是本项目的产品化建议，具体实现仍需详细设计：

1. 以组织、角色和规则表达职责，不写死两个老板、特定账号或国家与个人的对应关系。
2. 公司、部门、岗位、项目成员和登录权限分层；拥有项目角色不自动获得全部 HR 或财务权限。
3. 币种、语言、时区、工作日历、成本方法、考核周期与审批策略支持配置；地区薪资规则作为地区能力处理。
4. 项目类型提供合理默认模板，允许必要裁剪；不要求所有项目必须产生收入、奖金或员工考核。
5. 项目可按规则关闭；关闭后的既有财务、绩效和奖励记录可以按所属模块继续完成，避免状态互相锁死。
6. 核心业务与直播、珠宝行业扩展分开；行业指标提供有来源的数据，不改变通用核心模型。
7. 报表、导入和 AI 共用领域权限及校验；共享入口不能成为绕过规则的途径。
8. 模块可启用、可集成、可分版本交付；配置能力不等于为每个客户维护一份分叉代码。

不以本次“标准化”推断已批准建设公有云 SaaS、多租户计费、完整财务、招聘或所有地区工资功能。这些是后续产品范围与部署形态决策，不是标准产品名称自然附带的实现任务。

## 8. 下一步设计与实施顺序

1. 建立统一术语与能力地图，明确项目指标／人员绩效、资源计划／实际投入／出勤、奖金池／个人奖励／支付等差异。
2. 为项目、HCM、核算三个通用产品域分别定义业务对象、状态、角色和集成接口；形成能力来源清单。
3. 对照当前代码逐项标记保留、重构、迁移、补齐或集成。项目日期、投入百分比、奖金与 KPI 绑定和强制关闭门槛是优先梳理项。
4. 按模块设计标准默认流程和配置点，再设计菜单、页面及角色工作台。
5. 分阶段迁移，保留既有项目、假勤、考核、奖金和成本历史；新旧流程用版本或生效日期区分。
6. 使用多个通用项目场景验证，而非只用现公司的流程：内部改进项目、客户交付项目、持续服务项目；覆盖跨项目兼职、不同日历与不同考核周期。

后续实现验收应覆盖：计划与实际分离、跨项目资源冲突、成本来源可追溯、奖励与付款状态区分、项目关闭后的后续结算、组织与项目数据权限，以及既有直播和珠宝业务兼容性。

## 9. 飞书作为考勤数据来源

### 9.1 建议分工

考勤已经由飞书承载，建议将飞书作为考勤的权威来源。网站负责考勤数据接入、必要的只读查询，以及与项目资源、报表和核算的关联。标准产品需要完整的能力边界，并不要求每项能力都自行开发。

| 飞书继续负责 | 网站负责 |
|---|---|
| 考勤组、班次、打卡及考勤规则 | 外部员工与本系统人员映射、数据来源配置 |
| 请假、补卡、加班等现有办理与审批 | 获取业务需要的考勤统计和已生效假勤结果 |
| 对考勤结果进行更正和重新统计 | 同步更新、历史版本、同步时间与失败状态 |
| 出勤和假勤的源记录 | 项目排期的可用性参考、只读记录、相关报表 |

网站中可保留“考勤记录（飞书同步）”入口，以及集成设置中的“飞书连接、人员映射、同步状态”；新假勤申请和纠错返回飞书处理，不在两个系统重复审批同一件事。

### 9.2 已确认的接口能力与待联调项

飞书官方列有考勤统计与班次查询接口，见[官方考勤连接能力介绍](https://www.feishu.cn/content/909840720720)。开放平台还有[查询统计数据](https://open.feishu.cn/document/server-docs/attendance-v1/user_stats_data/query-3)、[查询打卡结果](https://open.feishu.cn/document/server-docs/attendance-v1/user_task/query)、[获取审批数据](https://open.feishu.cn/document/server-docs/attendance-v1/user_approval/query)入口。

本次开放平台页面正文未被网页读取工具展开，因此结合官方 Java SDK 文档确认接口类别：统计查询支持日度／月度数据，审批结果查询支持请假、加班、外出与出差的通过数据。[统计查询 SDK](https://larksuite.github.io/oapi-sdk-java/com/lark/oapi/service/attendance/v1/AttendanceService.UserStatsData.html)、[审批结果 SDK](https://larksuite.github.io/oapi-sdk-java/com/lark/oapi/service/attendance/v1/AttendanceService.UserApproval.html)。该 SDK 文档版本较早，不据此承诺当前字段、额度或权限限制。

实际实施前仍需在企业应用授权范围内验证：启用的飞书考勤产品、租户与员工覆盖范围、可读字段、统计表头、假期时长和计量单位、撤销与补卡后的返回行为，以及接口频率和时间区间限制。不能把“有接口”当成“本企业已授权且所有字段都可用”。

优先同步日／月统计及确有业务用途的有效假勤结果；只有需要下钻时才读取打卡明细。原始打卡定位、照片等不作为项目管理默认所需数据。

### 9.3 标准接入方式

1. **人员映射。** 建立外部提供方、企业／应用范围、外部 ID 类型和本系统员工的映射，不按姓名直接关联；核对所选 ID 的稳定范围，处理重名、离职和重新入职。
2. **后端授权。** 使用企业应用获得所需读取权限和数据范围；密钥与令牌在服务端管理，管理页面只显示连接状态。
3. **标准数据模型。** 将飞书结果转换成网站统一的考勤／可用性记录，保留来源标识、业务日期与时区、计量单位、版本和同步时间；业务服务不直接依赖飞书原始响应格式。
4. **查询与补偿同步。** 先实现按范围查询、初始历史同步、周期刷新和失败重试；回查近期记录以覆盖补卡、假期取消和统计修正。若当前接口提供适用事件，再增加事件触发刷新，不预设所有变更都有事件。
5. **业务使用。** 项目读取人员可用性，HR 页面只读展示，核算读取明确需要的结果。数据缺失、无权限或同步失败均标为未知／待同步，不推断为缺勤或零成本。
6. **历史与审计。** 同步重复执行不重复计数；来源更正保留变更轨迹。已锁定经营结果通过受控调整处理，不因一次后台同步静默重写。

飞书是首个数据提供方，接口设计仍以通用考勤数据契约为边界。以后需要接入其他考勤系统时替换适配层，不为当前只有飞书而构建多套并行集成，也不把飞书字段写死进项目和核算核心。

### 9.4 现有本地请假与项目成本的切换

现有请假记录与项目填报、人员成本重算直接关联。接入时不能只把飞书假期写进旧请假表后继续沿用原逻辑，也不能只隐藏申请按钮。

当前仓库尚未发现飞书 SDK／接口、外部员工 ID 映射或同步任务实现。已有本地请假还通过 `SetProjectMemberLeaveCapability` 提供 AI 操作，且 `BusinessProjectServiceImpl.java:2276` 附近存在未完结请假／销假阻断结项的校验；切换范围必须覆盖这些入口和规则。

- 保留本地历史申请、审批和来源；切换日之后的新考勤业务由飞书办理。
- 对切换前未完结申请单独列出并确定处理方式，避免在两个系统对同一事项重复执行。
- 同步调整本地请假接口与 AI 写入能力，避免网页移除入口后仍能创建新的本地申请；复核假勤未完结对项目关闭的硬阻断，外部同步延迟不能被直接当成不允许交付的业务事实。
- 将请假导致的资源不可用与具体任务安排分开；请假不代表交付任务已经取消，可调整排期或转交。
- 将“请假直接归零项目人员成本”的规则从数据接入中分离，具体成本处理服从核算方法。
- 项目实际工作量继续由项目／任务工作记录形成，不能把出勤一天自动分配到某项目，也不能给多个项目各记完整一天。
- 同步范围不等于网站可见范围；网站仍按公司、项目和人员角色控制展示，默认不向普通项目成员开放详细请假原因或附件。

本节为可行性结论与集成建议；尚未创建飞书应用、取得企业授权、同步真实考勤或停用网站现有流程。
