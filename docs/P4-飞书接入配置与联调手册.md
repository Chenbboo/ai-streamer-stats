# P4 飞书只读假勤：配置与联调手册

日期：2026-09-07。实现范围：只读来源、人员映射、同步批次、异常处理、组织查询授权和受控切换。真实企业授权与样本验收仍须由管理员配置并逐项记录，本文件不代表真实企业已经联调通过，也不代表代码已部署。

## 1. 入口与权限

| 入口 | 权限 | 额外业务范围 |
|---|---|---|
| 系统与集成 → 飞书连接与同步 | `business:integration:feishu` | 技术人员管理连接、映射、补拉及同步问题；不会因此获得假勤明细或薪酬权限 |
| 人力资源 → 飞书假勤查询 | `business:attendance:self` | 本人记录；默认不显示公司全量数据 |
| 人力资源 → 飞书假勤查询 | `business:attendance:read` | 公司实际负责人，或经其授权的组织读取范围；角色权限和组织范围同时满足 |
| 人力资源 → 假勤接入验收 → 验收与切换／组织查询授权 | `business:attendance:cutover` | 必须是当前公司的实际负责人，技术管理员不能代替业务验收 |

只有切换权限的负责人也能进入连接列表，列表仅显示本人负责公司的必要连接信息；不会调用技术映射接口。该负责人可阅读同步批次与问题编号，登记真实验收与组织读取范围。仅有本人查询权限的员工无需飞书技术权限。

## 2. 服务端配置

应用仅读取下列服务端环境变量，前端和数据库不接收应用密钥。不得把真实密钥提交到仓库、聊天、截图、验收说明或命令输出中。

| 环境变量 | 用途 | 默认 |
|---|---|---|
| `FEISHU_ATTENDANCE_ENABLED` | 允许适配器发起飞书只读请求 | `false` |
| `FEISHU_APP_ID` | 企业自建应用 App ID | 空 |
| `FEISHU_APP_SECRET` | 企业自建应用 App Secret | 空 |
| `FEISHU_TENANT_KEY` | 应用所属企业标识，须与连接一致 | 空 |
| `FEISHU_ATTENDANCE_POLL_ENABLED` | 启用定时补拉 | `false` |
| `FEISHU_ATTENDANCE_POLL_DELAY_MS` | 定时补拉间隔，毫秒 | `900000`（15 分钟） |

配置完成后重启后端进程。界面只显示各项是否存在，不返回密钥或 token。首版服务进程使用一组企业自建应用凭据，可为该企业内多个本地公司分别建立连接和人员范围；不同飞书企业不能复用同一环境凭据。

应用需要由企业管理员授权以下能力及指定员工范围：企业信息查询、考勤结果查询、审批数据查询、每日排班查询、班次详情查询。实际可用权限以飞书开放平台当前应用后台为准。不能用“接口返回成功”替代确认员工可读范围。

首次发起读取时，适配器获得 tenant token 后调用企业信息查询，核对真实 `tenant_key`；不匹配立即失败。每次 token 更新重新验证企业归属。应用凭据和来源响应均不写入普通操作日志。

## 3. 人员映射与数据归属

每条映射记录本地 `sys_user.user_id`、连接公司／企业、外部 `employee_id`、生效开始日和可选截止日。`employee_id` 是本适配器调用考勤接口时显式选择的 ID 类型，不与 `employee_no`、`open_id` 自动混用。

通过人工确认的员工标识建立映射，不按姓名或手机号自动匹配。对同企业外部身份和本地人员有效期做冲突检查，并锁定企业映射范围，防止并发跨公司串人。截止日包含在原映射内；改绑应先明确旧映射结束日，再建立新区间。不能将旧映射截止日设在已经产生的历史来源日期之前。

每次映射变更增加连接版本，使旧同步／验收不能用于新版本切换。已有来源记录继续关联当时的映射，不批量改写历史归属。飞书员工不会自动创建本地账号或获得角色权限。

## 4. 已验证的接口与字段映射

以下是编码时检查的飞书官方 SDK 字段，核查日期为 2026-09-07；真实企业样本仍须进一步验收。适配层版本为 `FEISHU_ATTENDANCE_V1_20260907`。

| 资源 | 请求 | 读取的最小字段／规则 |
|---|---|---|
| 企业信息 | `GET /tenant/v2/tenant/query` | `data.tenant.tenant_key` 与配置比对；不保存企业头像等信息 |
| 审批结果 | `POST /attendance/v1/user_approvals/query?employee_type=employee_id` | `user_ids`、`check_date_from/to`、`check_date_type=PeriodTime`；分别查询 `status=2`（通过）、`3`（撤回） |
| 请假规范化 | `data.user_approvals[].leaves[]` | `approval_id`、开始／结束、本源时区、`interval`（源端认可秒数）及单位；不保存请假理由 |
| 考勤结果 | `POST /attendance/v1/user_tasks/query?employee_type=employee_id` | `result_id`、`user_id`、`day`、每段 `check_in_result/check_out_result`；明确检查 invalid／unauthorized IDs |
| 每日排班 | `POST /attendance/v1/user_daily_shifts/query?employee_type=employee_id` | `user_id`、`month`、`day_no`、`shift_id`、`is_clear_schedule`；清空排班保留未知状态 |
| 固定班次 | `GET /attendance/v1/shifts/{shift_id}` | 固定上下班区间减去休息区间；支持 `26:00` 这类跨次日表示 |

上述三个查询接口在当前官方 SDK 中没有分页 token。应用按一天、最多 10 名人员一片调用，并记录资源、日期、分片编号、范围摘要、成功／失败状态和计数。一次手工补拉最多 7 天，查询结束日不超过源时区的明天。真实平台限制改变时应升级适配器，不臆造游标分页参数。

来源键：请假按企业连接、员工、审批实例及业务日组成；同一实例／业务日出现多条无法确定唯一归属的记录，整片拒绝并生成问题，不按顺序合并。考勤结果使用 `result_id`；每日排班使用员工与业务日。持久化来源键使用 SHA-256 摘要，并保留必要审批实例或班次引用。请假类型、起止时间和状态属于可变化内容，不纳入稳定主键。

`sourceRevision` 是本地保留的来源修订序号，不能冒充飞书返回的可排序版本。无外部可排序版本时，整片串行读取并复查同一范围，内容变化则本次不覆盖；并用数据库运行租约防止迟到进程覆盖后续批次。重复内容仅更新最近见到时间，不新增修订；更正或明确撤回新增修订，原修订仍能查询。

缺项、接口错误、权限缩小、未完整读取不会推断撤销，也不会删除旧记录。正常出勤不生成项目投入，假勤同步不写人工成本，不自动重开历史核算。

如果新完整批次覆盖同一业务日却未再返回某条旧记录，保留旧来源状态及历史，同时将该当前记录标为不完整，不再据此提供精确可用容量。记录同时保留最初写入批次 `syncRunId` 与最近实际读到的批次 `lastSeenRunId`，幂等回放不伪造新修订。

## 5. 可用性与未知情况

可用性仅在已经切换的范围、有覆盖该业务日的完整同步、有效固定班次和可解释记录时提供。班次跨午夜仍按源业务日归属；请假先合并重叠区间，再与有效工作区间相交，午休不重复扣减。源端认可的请假时长和自然时间跨度分别保留。

弹性／复杂班次规则、缺少排班、源端未知枚举、读取不完整及过期数据标记 `UNKNOWN`、`PARTIAL` 或 `STALE`。首版不会把尚未支持的弹性班次假定为八小时，也不提供伪精确的零容量。未来日期超出该 API 支持范围时，项目计划可继续依据独立版本化工作日历，但不能称为飞书已核实容量。

只读页面显示实际来源枚举、时区、区间、源端认可时长、来源批次和修订；“已读取”表示来源记录可解释，不等于人工真实样本验收已经通过。

## 6. 同步、补拉与问题处理

“启动补拉”立即返回已持久化的运行编号；既有应用线程池在后台处理，每片提交后更新进度。数据库租约防止同连接并发；过期执行权不能推进新批次水位。应用中断后的运行可以在租约超时后补拉，旧运行保留失败记录。

自动补拉默认关闭。开启后启动约 10 秒发起首次补拉，此后每隔配置时间回看最近 N 天（含今天）；`FEISHU_ATTENDANCE_POLL_LOOKBACK_DAYS` 默认 3，限制为 1～7 天；更久远的更正使用指定日期范围手动重放。API 429／5xx、网络失败做有限重试；持续错误留在运行记录中，不无限循环。只有全部资源分片完成，才更新完整同步水位。

同步问题包括来源变化、无法解释的状态／班次、人员授权范围不足、历史身份冲突等。技术人员填写核实依据后关闭问题待办；该操作不会修改飞书事实或批准业务单据。涉及已确认投入／金额的来源更正，应由对应业务人员在项目或核算的更正流程中处理，不能通过关闭同步问题代替。

## 7. 真实联调与切换

推荐顺序：

1. 按备份及维护窗口要求应用 V066 和后续菜单迁移，配置服务端授权。
2. 集成管理员建立公司连接，逐人核对外部标识及有效期；先保持 `PARALLEL`。
3. 对真实员工、真实日期进行只读补拉。核对授权范围、日期、时区、实例键和记录状态。
4. 公司负责人登记六类真实情景：正常出勤、已通过请假、更正／撤回、跨日、未映射／范围异常、故障后恢复。记录预期、飞书来源证据、本地实际结果、说明和是否通过。
5. 每个情景必须关联实际批次和来源记录／已处理的问题；更正样本要求来源修订，跨日样本要求真实跨日区间，正常样本要求正常考勤结果。恢复样本关联故障之后实际完成的补拉。

   来源记录可引用其最初写入批次或最近实际读到的批次；两种批次都必须完整成功且对应当前映射版本。因此同内容幂等回放也能完成核验，不需人为改动来源以制造修订。
6. 处理全部本地待批准／待撤销申请，并处理所有已批准但跨切换生效日的本地假勤，不由系统伪造取消或审批。
7. 选择至少为来源时区明天的生效日。系统独立检查当前映射版本、全体在职人员映射、最近 48 小时且覆盖最近业务日期的完整同步、待处理问题和六类验收。
8. 实际公司负责人明确确认后变为 `ACTIVE`。按生效日关闭相应范围本地新办理；生效日前历史按原流程和原成本版本保留。

公司范围通过人员所属公司和提交项目公司共同检查，按公司 ID 顺序加锁，避免跨公司项目成员绕过来源切换。最终守卫使用数据库当前读，避免事务内先前读取的快照漏掉已经提交的切换；同步连接锁不会反向取得公司锁。页面、API 和 AI 使用同一业务写入守卫。AI 过期确认卡不能越过最终事务校验。

服务端关掉同步开关、密钥失效或飞书故障都不会恢复本地请假申请。保留最近来源快照与故障标记；若需要临时人工流程，必须另外明确业务范围、有效期和去重处理，不能将技术回退当作自动重新开通本地办理。

## 8. 验证范围与官方依据

自动化覆盖：缺凭据不外呼、企业和人员范围、通过与撤回状态、最小字段、午休与重叠区间、跨日、未知班次、重复同步、来源修订、部分失败水位、公司读取授权、技术权限隔离、切换阻断、历史兼容及 AI 过期确认。

自动化只使用测试数据。当前未在本批任务中记录真实企业正常／假勤／更正样本，因此不可手工修改数据库绕过验收，或宣称已完成真实企业切换。真实授权配置完成后的接口结果与业务对账记录应继续登记在系统验收页。

## 8. 日考勤展示（2026-09-07 补充）

员工假勤查询改为一人一天一行：排班时间、实际上下班打卡、飞书考勤结果、请假时段及已通过补卡。多段班次逐段展示，跨日打卡显示完整日期；没有记录不推断缺勤。按现有本人/公司范围授权读取当前修订，收齐来源分页后再按人员与日期聚合，避免同一天的记录被分页拆散。

适配器 V2 保存 `user_tasks.records.check_in_record/check_out_record.check_time`（秒时间戳）以及独立的计划打卡时间；缺失或零时间不替换为排班时间。仅保存必要时间字段，仍不保存地点、设备、照片或理由。查询 `user_task_remedys/query` 的已通过记录（status=2），在 TASK 分片内一并校验；接口失败则分片失败。页面“未见已通过记录”不表示没有待审批补卡。

旧来源仍保留历史；需要对目标日期重新补拉，才会补齐实际打卡时间。后台最近读取判断兼容 Connector/J 返回的 LocalDateTime 与传统 Date，避免刚同步记录被误标陈旧。


## 10. 批量员工关联与同步运维（2026-09-08）

- 技术管理员在“人员映射 → 从飞书批量关联”读取授权名单。使用通讯录 scope、部门子级、部门直属用户和用户详情接口，员工始终采用 `user_id`，部门采用 `open_department_id`（当前授权的部门响应可能不返回 `department_id`）；支持逐页读取和去重，只返回标识、姓名、不可用状态。接口失败、分页游标重复或超出读取上限时整份名单失败，不展示为完整名单。
- 当前单次完整名单限制：200 个部门、2000 名员工、每个分页接口最多 100 页、读取预算 120 秒（单个在途请求可能额外占用网络超时）。前端请求超时 180 秒。超出范围需缩小应用授权范围或扩展为后台通讯录同步作业，不能宣称支持任意规模企业。
- 姓名仅生成建议。重名不预选账号，已绑定人员不可重复选，管理员必须勾选并确认身份、账号和生效日期。可一次保存 1～50 人。后端重新读取当前授权范围，检查公司、在职状态、映射版本、有效期和重复身份，并在一个事务中保存；任一项失败整批不写入。不会创建账号或分配角色。
- 接口：`GET /business/feishu/{id}/directory`、`POST /business/feishu/{id}/mappings/batch`、`GET /business/feishu/{id}/sync-overview`。均要求 `business:integration:feishu`；新增读取范围为身份和同步覆盖元数据，不含打卡明细或薪酬。
- “同步记录”展示服务端实际启用状态、周期、回看天数和当前有效关联人数。“查看人员覆盖”展示来源记录最早/最晚日期、已读日期数、最近读取时间；不把最早与最晚之间的每一天视为已覆盖，不将缺记录推断为缺勤。
- 失败/部分成功批次提供“按原范围重试”：用原日期窗口发起新批次，读取当前有效映射，保留原失败记录，使用既有数据库租约防止并发。历史补拉每次仍最多 7 天，超过 7 天由管理员分段操作。
- 单个后端实例中通讯录、考勤、鉴权与重试共享每秒 5 次的请求节流。现有 API 429/5xx 最多尝试 3 次，不无限重试；多实例部署仍需按实例数协调额度，不将单机限流视为跨实例总限流。
- 定时任务可恢复租约过期的中断批次；仍有效的 JDBC `LocalDateTime` / `Timestamp` 租约不能被抢占。正式来源切换和真实业务样本验收仍按第 7 节执行。

接口依据：[通讯录授权范围](https://open.feishu.cn/document/server-docs/contact-v3/scope/list)、[部门直属用户](https://open.feishu.cn/document/server-docs/contact-v3/user/find_by_department)、[飞书官方部门遍历示例](https://github.com/larksuite/oapi-sdk-python-demo/blob/main/composite_api/contact/list_user_by_department.py)。
