# 飞书考勤：集成契约与切换设计

> 版本：v1.1
> 日期：2026-09-07
> 状态：下一阶段设计稿；未接入真实飞书企业，接口字段、授权范围及样本尚待联调核实
> 关联：[标准产品蓝图](./标准产品蓝图.md)、[项目业务流程与数据设计](./标准项目管理-业务流程与数据设计.md)、[改造差距与实施清单](./标准产品-改造差距与实施清单.md)
> v1.1：明确人力资源假勤查询、项目可用性消费与共享平台集成管理的归属，接入和切换范围不扩展；先看[三系统拆分方案：审阅版](./三系统拆分方案-审阅版.md)。

## 1. 业务边界

飞书继续办理排班、打卡、请假及其审批、补卡和考勤纠正。本网站接入必要结果，支持人员可用性判断、只读查询和项目安排。网站不再扩建本地考勤规则、打卡或请假审批系统。

本网站继续拥有项目成员安排、项目实际投入、投入确认及项目成本依据。出勤不能说明员工具体做了哪个项目，缺少飞书数据不能视为缺勤，也不能直接把当日人工成本清零。

| 数据／行为 | 权威来源 | 网站职责 |
|---|---|---|
| 打卡、考勤规则、补卡、假勤审批 | 飞书 | 按授权读取必要结果，展示来源与更新时间 |
| 网站假勤结果查询及待核实记录 | 飞书原始事实，人力资源管理系统提供只读视图 | 按组织和敏感字段权限展示，不在本地审批或修改飞书事实 |
| 外部人员标识 | 飞书 | 与本地稳定人员标识建立明确映射 |
| 飞书连接、人员映射及同步监控 | 共享平台的集成管理 | 配置连接与映射、处理同步异常；技术权限不自动授予假勤、绩效、奖金或财务数据权限 |
| 网站账号、角色和业务数据权限 | 本地平台 | 保留现有授权；外部员工同步不自动授予权限 |
| 项目人员安排、计划工作量、实际投入 | 项目管理 | 独立记录和确认，必要时提示假勤冲突 |
| 内部成本单价、成本确认、调整及关闭 | 财务与管理核算 | 根据已确认成本政策处理，不由同步任务直接改账 |

这里的“集成契约”是本地规范化数据设计，不是声称飞书接口已具有下列字段。外部字段映射表在真实企业联调后冻结版本。

## 2. 接入对象与授权前置

首轮优先读取人员标识、排班／工作日依据、已审批假勤结果和必要日统计；是否需要打卡明细由核实后的业务需要和授权决定，不默认保存定位、照片或设备明细。

正式联调需要企业管理员提供或配置：应用与企业关联、授权范围、可读取人员范围、接口可用能力、时区和业务日期口径，以及正常出勤、请假、撤销／更正和跨日场景样本。应用凭据通过服务端密钥配置保存，文档和前端不接收密钥明文。

官方考勤文档提供统计、考勤任务、审批结果和每日排班等查询入口；具体返回字段、分页方式、时间范围限制、频率限制和审批修正表达方式，必须以当前 API 文档与企业实际返回为准。本轮未取得真实租户数据，不能承诺现成映射或同步成功。

这些前置只阻塞外部联调与启用，不阻塞项目状态拆分、模块边界调整、适配层开发和模拟数据验证。

## 3. 人员映射

### 3.1 逻辑对象

| 对象 | 建议字段 | 约束 |
|---|---|---|
| `IntegrationConnection` | id、provider、enterpriseScope、appScope、status、secretRef、capabilityVersion | 一个明确的企业与应用授权上下文；凭据仅通过引用解析 |
| `ExternalPersonMapping` | connectionId、idType、externalId、localUserId、effectiveFrom、effectiveTo、status、confirmedBy | 外部标识按企业、应用和标识类型定界；同一外部标识有效期不得映射至两个人 |
| `MappingIssue` | externalIdentity、reason、detectedAt、resolution、resolvedBy | 未匹配、重复、失效和范围变化均进入待处理记录 |

本地继续以现有 `sys_user.user_id` 关联业务历史，不以手机号、姓名或飞书外部 ID 替换历史主键。企业人员标识和应用人员标识不混用；不同连接间只有经确认的关联可以合并身份。

姓名或手机号可作为人工匹配的提示，不能单独作为自动绑定依据。建立、改绑、停用映射需要有权限的管理员操作并留审计。改绑不批量改写历史考勤所属人或历史成本，必须先核查影响。

离职、账号停用或外部授权范围缩小，不删除历史记录。外部新增员工不自动获得本地项目、薪酬、财务或管理员权限。一个人在多个公司任职时，公司归属按有效期和业务授权处理，不能仅凭外部企业相同放开全公司数据。

### 3.2 未匹配策略

未匹配记录进入隔离区，仅集成管理员可排查；项目经理不得看到未知员工的全量假勤。完成映射后可重放允许范围内的同步窗口，并保留原始接收时间和重新处理记录。

## 4. 本地规范化数据契约

| 对象 | 建议字段 | 用途与约束 |
|---|---|---|
| `AttendanceObservation` | id、connectionId、mappingId、localUserId、sourceRecordKey、sourceRevision、businessDate、sourceTimezone、kind、normalizedStatus、sourceStatus、observedAt、receivedAt、syncRunId、mappingVersion | 保存外部事实和转换依据，未知状态不强行映射为正常／缺勤 |
| `AttendanceInterval` | observationId、startInstant、endInstant、sourceLocalStart、sourceLocalEnd、durationMinutes、durationBasis | 区分真实时间跨度与源端认可时长；二者不能默认相等 |
| `WorkCalendarObservation` | connectionId、localUserId、businessDate、workingIntervals、expectedMinutes、sourceTimezone、sourceRevision、quality | 为可用性提供排班依据；排班未知不能按全天休息处理 |
| `AvailabilityProjection` | localUserId、businessDate、plannedCapacityMinutes、approvedUnavailableMinutes、availableMinutes、quality、derivedFrom、calculatedAt | 可重算的派生结果；不是出勤结论，也不是项目实际投入 |
| `SyncRun` | connectionId、resourceType、requestedScope、windowStart、windowEnd、cursor、coverageStatus、status、receivedCount、rejectedCount、startedAt、finishedAt、errorCode | 记录这次到底读取了什么、是否完整及失败原因 |

`normalizedStatus` 建议包含已确认、撤销／失效、待解释和未知等语义，具体枚举按资源类型设计，不能把不同 API 的状态码直接合并。审批尚未完成与审批结果缺失是两种情况。

`quality` 与业务状态分开，建议表达 `KNOWN`、`PARTIAL`、`STALE`、`UNKNOWN`：数据陈旧不等于员工缺勤，部分同步不等于完整当天记录。

每条规范化记录必须能追溯来源、连接、人员映射、业务日期、转换版本和同步批次。原始响应仅保留排障和审计必要字段，并设置访问范围与保留期限；正常业务页面使用规范化结果。

## 5. 天、分钟与可用性计算

项目安排支持工作小时和人天，内部用整数分钟存储。工作日历计算可用容量，独立的单位政策规定分钟／人天，二者分别保存版本和快照。日历变为六小时工作日，不自动改变既有人天换算；也不能固定假设每个人每天都是八小时。老板视图可汇总显示人天，仍保留换算依据。

可用性按“有效工作区间与已确认不可用区间的交集”计算：跨日区间按来源时区、业务日期规则和工作区间归属处理，先合并重叠请假，避免重复扣减。不能用请假开始到结束的自然时间跨度直接扣工作量。

示例（仅作验收样例）：某天工作区间为 09:00—12:00、13:00—18:00，已批准请假为 11:00—14:00，交集为 2 小时，当天可用 6 小时。另一条重叠请假不能再次扣掉同一小时。

计划容量、已安排工作量和实际投入分别保存。排班及已批准的未来请假可用于预测可用性；已发生的出勤结果只说明过去情况，不能直接推算未来容量。假勤与已填报项目投入冲突时生成待核实事项，不静默覆盖已确认实际投入。

外部排班无法读取时，可以使用有明确来源和生效版本的本地项目工作日历作为计划依据，并标明未核实外部排班；不能展示为“飞书已确认可用”。没有可用依据时显示未知，不输出伪精确的人天或零成本。

## 6. 同步、修正与幂等

### 6.1 调度方式

接入先以受控查询和定时拉取完成闭环。同步频率、历史回看窗口和失败重试间隔可配置，按官方限额与实际规模确定，不在设计中假定接口支持固定分钟级刷新。只有确认所需事件及撤销／修正事件可用后，才把事件作为触发补充；仍需补拉和对账。

适配层可抽象为 `AttendanceProvider`，提供能力描述、人员标识读取、排班查询、假勤结果查询和统计查询。各能力可标明不支持、未授权或暂时不可用；不能用成功空数组掩盖失败。该抽象不要求引入新框架、独立服务或消息队列。

### 6.2 每次运行

1. 固定本次连接、授权人员范围、资源类型、时间窗口和映射版本，并记录运行编号。
2. 按经过验证的分页规则读取，保留每页成功／失败与完整性。失败页不能推进整个窗口的成功水位。
3. 校验外部身份、时间、状态和版本；未知记录隔离，已知记录按幂等键写入来源层。
4. 规范化后更新可重算的可用性视图，并生成冲突或变更待办。
5. 只有窗口满足约定完整性条件后才推进对应资源和范围的成功水位；部分成功有独立标记，可安全重试。
6. 展示最近完整同步时间、当前失败／陈旧状态、未映射数量和待核实数量；同步错误不影响本地其他业务读写。

若外部资源提供稳定记录 ID，则以连接、资源类型、记录 ID 作为来源主键，保留源版本和本地修订序号。若没有稳定 ID，必须先验证该资源可组成稳定自然键的字段，再冻结键的构成和冲突处理方式；不能仅用“人员＋日期”合并一天内多条审批。

重试同一数据不会重复新增请假或重复扣减容量。同一来源的新修订更新当前有效投影，同时保留旧修订。外部没有可排序版本时，延迟返回可能覆盖新数据的风险必须通过复查当前窗口、批次顺序和对账消解，不能仅比较本地接收时间就认定业务版本更新。

撤销或删除只能依据明确的源端状态／删除信号，或经过验证的完整权威窗口对账规则判断。接口报错、权限缩小、分页中断或结果缺项，均不能直接删除本地历史数据。

### 6.3 与费用和关闭状态的关系

来源修正可以刷新当前可用性，但不直接修改已确认项目工时、已确认成本或历史关账结果。产生金额影响时，记录来源差异、受影响业务单据和待处理建议，由授权业务人员按原单更正、调整或冲销流程处理。

项目已经交付并不意味着所有核算已经关闭；项目核算关闭也不等同于未来企业会计期间锁定。无论处于哪种关闭状态，同步都不能自行重开账或越过对应限制。

## 7. 权限、界面与审计

三个业务系统下的入口分别归属：人力资源管理系统提供只读假勤查询；项目管理系统消费必要可用性与冲突提示；财务与管理核算系统查看获授权的成本相关证据。连接、人员映射和同步监控位于共享平台的集成管理，不在 HR 中增建本地考勤办理功能。

| 使用者 | 可见内容／操作 | 限制 |
|---|---|---|
| 员工 | 本人相关假勤结果、来源和更新时间；前往飞书办理 | 本地只读，不能在这里审批或纠正飞书原记录 |
| 项目经理 | 所管项目成员的必要可用性与冲突 | 默认不展示请假原因、定位、其他项目或全公司假勤明细 |
| 人事授权人员 | 授权组织范围内必要假勤与待核实记录 | 仍受公司和敏感字段权限控制 |
| 集成管理员 | 连接健康、映射、失败重试和授权范围配置 | 技术配置权限不自动包含薪酬查看或业务审批权限 |
| 核算人员 | 与成本处理相关的证据及差异 | 来源记录可追溯；不把同步控制台当作成本修改入口 |

页面明确区分“飞书结果”“历史本地记录”和“项目投入”。来源异常时保留最近有效快照并显示陈旧标记；需要最新依据的业务操作提示待核实，不用零值冒充最新结果。

飞书跳转入口仅使用经确认的合法应用入口或深链规则，不能假设每条考勤记录都有可直接打开的网页链接。接口日志遮蔽凭据和敏感内容，映射变更、手工补拉、版本切换及业务更正均记录操作人。

## 8. 本地请假退出与切换

当前网站实际存在的是本地项目请假及审批、核算联动，不应把它描述成已经具备完整考勤产品。现有请假可影响多项目日核算，因此不能先删菜单再假定接入完成。

| 阶段 | 动作 | 进入下一阶段的条件 |
|---|---|---|
| 未启用 | 接入开关关闭，记录当前本地流程和历史基线 | 适配层与权限设计可独立开发 |
| 已配置 | 配置应用、授权和范围，建立人员映射 | 连接验证通过，关键人员映射无冲突 |
| 并行核对 | 飞书只读同步；本地原流程暂按既有规则运行 | 真实样本核对通过；同步记录不会双重影响成本 |
| 切换准备 | 确定公司／人员范围、生效时间和数据归属；逐项处理未完本地申请 | 未完申请有明确收尾负责人、截止方式和审计记录 |
| 正式启用 | 对已切换范围停止本地新请假与新审批入口，页面／API／AI 同步限制；飞书结果进入可用性 | 验收通过，异常处理与回退已演练 |
| 历史只读 | 旧本地假勤按旧来源查询，已核算数据保持历史口径 | 持续对账，差异通过有权限的更正流程处理 |

同一有效时间段必须有明确的假勤权威来源规则。并行核对期间不会把飞书结果和本地请假同时计入不可用量；对疑似重复记录先标记关联并核实，不用姓名和日期直接删除历史记录。

切换边界以前的未完申请可在旧流程中限范围办结，也可在核实后撤销并在飞书重新办理；不能替用户自动代办或伪造批准。切换完成条件要求这些选择已经逐条处理，不能留两套长期并行的审批入口。

切换与核算政策版本分别记录。新考勤来源并不自动把旧版百分比分摊改成新版实际投入核算，旧成本历史需可重现。具体代码改动参见实施清单中的本地请假和飞书接入事项。

回退先停止新同步和派生更新，保留最后有效快照、失败状态及全部审计。已经确认的投入／成本不倒灌覆盖。是否恢复本地临时受理必须另设明确的范围、时间和去重规则，不能由自动回退顺便重新开启全站请假审批。

## 9. 验收情景

| 编号 | 场景 | 预期 |
|---|---|---|
| F01 | 同名员工、不同企业／应用标识 | 不自动串人；没有授权或映射的记录隔离 |
| F02 | 已离职人员、历史映射变更 | 历史仍可追溯，不新授予账号权限，不静默改历史所属人 |
| F03 | 正常排班＋午休内跨段请假 | 仅扣工作区间交集；同一请假重复拉取不重复扣减 |
| F04 | 跨午夜或不同时区的排班／请假 | 按验证的业务日期和时区规则归属，时长不因字符串截日期而丢失 |
| F05 | 请假撤销、已读取结果后续更正 | 保留修订并更新可用性，已确认成本生成待核实差异而非直接改写 |
| F06 | 部分分页失败、接口限流、权限缩小 | 标记部分／陈旧，成功水位不误推进，不把缺项当撤销或缺勤 |
| F07 | 多条重叠请假或缺少排班依据 | 重叠区间合并；无可靠日历时明确未知，不产生虚假零成本 |
| F08 | 外部正常出勤但本地未填项目投入 | 不自动替员工生成项目实际工作量 |
| F09 | 普通成员、跨项目经理、核算员、技术管理员查询 | 分别按业务范围及字段权限返回；不因拿到外部标识即可越权 |
| F10 | 本地申请未完、正式切换及故障回退 | 不出现双重计量；旧申请可追溯；页面、接口和 AI 均遵守同一来源边界 |

上述情景先用脱敏模拟数据验证适配与业务约束，再对真实授权企业至少核实正常、请假、更正、跨日及未匹配样本。真实校验必须记录期望、外部事实、本地结果及差异，不以“接口返回 200”代替验收。
