# 子项目进度汇报

子项目列表操作栏与详情页顶部提供「汇报进度」。仅当前子项目主负责人本人可以提交，管理员和总项目负责人不能代填。执行中、暂停的子项目可汇报；已结项、已取消、已删除的项目只保留查询入口。

表单包含 0–100 的整数进度、阶段成果、问题风险、下一步计划。问题风险无内容时填「无」。汇报人、日期、时间、版本号由服务端生成；客户端传入的身份、时间、版本、快照会被忽略。纠正时可以下调进度，但必须提交新版本。

一次性任务与持续工作的当前执行情况自动带入，可分别勾选是否随汇报展示。提交时服务端重新读取任务、任务填报、持续工作当日执行与累计成果、关联直播来源数据和执行区间，保存独立 JSON 快照。即使没有勾选同步，完整快照仍可在历史记录中展开查看。后续修改关联数据不改变旧快照。

每次提交在同一数据库事务内追加汇报、写入子项目及总项目动态、生成面向总项目负责人的站内通知。动态链接和通知均能定位到子项目的具体汇报版本。通知位于顶部消息入口，打开时刷新，并每 60 秒检查更新。总项目负责人仅查看原汇报；负责人变更后，原接收人仅保留已通知给自己的历史版本读取权，不获得后续汇报或实时任务数据权限。

总项目进度 = 四舍五入（Σ 子项目进度 × 权重 / Σ 权重）。未设置权重按 1 计算；未汇报的执行中子项目按 0 计算。沿用既有状态口径：已结项子项目为 100，已取消子项目为 0。已删除子项目不参与当前汇总，汇报档案继续保留。总项目负责人可以在汇总面板配置正数权重，最多 4 位小数，留空恢复默认等权。有子项目的总项目不能手工填报覆盖汇总值。

历史记录只追加，无修改、删除接口。项目软删除后，可以通过原通知、动态或总项目汇报档案读取快照。原系统曾经覆盖掉的同日旧内容无法恢复；迁移前保留下来的记录继续显示，缺少快照时明确标注，不用当前数据冒充历史数据。

## 部署

先按顺序执行数据库迁移至 `V090__immutable_subproject_progress.sql`，再发布后端与前端。V090 移除每日唯一约束、新增汇报快照字段和查询索引、子项目权重、定向通知表，并回填既有记录的项目名称和父项目关联。迁移由现有部署流程执行一次，不要在旧后端仍写入时混合运行新旧版本。

执行 `verify_business_schema.sql` 验证 V090 检查项均为 0。不要通过重新创建每日唯一约束回滚：同一天现在可能有多个合法版本。

## API

- `POST /business/project/progress-report`：提交新汇报；服务端严格校验主负责人。
- `GET /business/project/progress/{projectId}`：汇报工作区、历史和快照；独立进行项目范围校验。
- `PUT /business/project/progress/{parentId}/weights/{projectId}`：总负责人配置权重，正文 `{ "weight": 3 }`，传 `null` 恢复默认。
- `GET /business/project/progress/notifications`：当前用户自己的通知。
- `PUT /business/project/progress/notifications/{id}/read`：仅通知接收人可标记已读。

## 验证

服务层测试覆盖本人提交、禁止管理员/总负责人代填、输入校验、忽略伪造身份和快照、下调进度的新版本、只读权限、删除后追溯、交接后通知历史范围。MyBatis + H2 集成测试覆盖同日多版本、最新值读取、等权/加权/缺报/已删除子项目、通知隔离和事务回滚；H2 验证应用 SQL，不替代部署环境的 MySQL 迁移执行。

前端测试：`node --test frontend/src/utils/projectProgress.test.js frontend/src/utils/projectHierarchy.test.js`。生产构建：在 `frontend` 运行 `node node_modules/vite/bin/vite.js build`。浏览器交互使用独立模拟数据验证表单、同步勾选、提交后的新旧版本、只读查看及汇总展开，没有向业务数据库提交测试汇报。
